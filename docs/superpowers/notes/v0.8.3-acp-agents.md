# Research: ACP subscription agents for Dom (v0.8.3 W8 / R14)

Question: can the owner's Claude, ChatGPT/Codex and Google AI subscriptions power Dom's own model turns through the Agent Client Protocol? Every web source was read on **2026-11-23**. Where something is undocumented, this report says so and does not guess.

## Summary

- **No-go for all three consumer subscriptions as the engine of an always-on Telegram bot,** on terms alone:
  - **Claude:** Anthropic's consumer terms bar access "through automated or non-human means, whether through a bot, script, or otherwise" except with an API key or where Anthropic explicitly permits it, and its Claude Code page says developers should use API keys.
  - **Antigravity (Google):** its terms call "using third party software, tools, or services to access the Service (e.g. using OpenClaw with Antigravity OAuth)" a breach. A Google forum reply allows a private, single-user, *interactive* client but excludes unattended automation. Gemini CLI's Google-account login stopped on 2026-06-18.
  - **Codex (OpenAI):** the least restrictive. OpenAI documents a supported way to run Codex unattended on a ChatGPT login ("trusted private automation"), but still calls API keys "the right way to authenticate automation". It is the only candidate for a pilot, owner DM only.
- **None meets Dom's zero-data-retention rule.** Consumer plans keep conversations (Claude: 30 days with training off, five years with it on; ChatGPT and Google can train unless the owner opts out).
- **The protocol itself fits.** An ACP agent can be driven from Python over stdio, returns text, and can be started with no tools of its own. But turning off built-in tools is *per agent*, not part of ACP, and the adapters' docs do not state a clean switch.
- **Recommendation:** do not build the subscription provider in v0.8.3. If the owner accepts the terms risk for Codex, build one small `acp` provider kind behind a switch, for owner-DM escalation and drafting only. Section 6 gives the minimal design.

## 1. The protocol

- **Spec:** <https://agentclientprotocol.com> (read 2026-11-23). JSON-RPC 2.0 over stdio, client launches the agent as a subprocess. The doc site has **v1** (stable) and **v2** (marked Preview: "v2 is not frozen yet" in the Claude adapter's README). The latest schema release found is `schema-v1.34.1`, published 2026-11-21 (<https://github.com/agentclientprotocol/agent-client-protocol/releases>). The v1 initialization example sends `"protocolVersion": 1`. Use v1.
- **Python client library:** `agent-client-protocol` on PyPI ("Pydantic models, async base classes, and JSON-RPC plumbing … for both sides"), <https://agentclientprotocol.com/libraries/python>. It would be a new dependency, which a hand-written JSON-RPC client over `asyncio.subprocess` could avoid (about 150 lines for initialize, session/new, session/prompt, the update notifications and cancel).
- **Lifecycle** (<https://agentclientprotocol.com/protocol/v1/overview>):
  1. `initialize` (versions and capabilities); then `authenticate` if the agent advertises auth methods.
  2. `session/new` (cwd and `mcpServers`), or `session/load` to resume.
  3. `session/prompt` with the user message. The agent streams `session/update` notifications (text chunks, tool calls, plans), may ask `session/request_permission`, and ends the turn by answering `session/prompt` with a stop reason. The client can send `session/cancel`.
  4. v2 changes this: the prompt response acknowledges acceptance and an idle `state_update` with a stop reason ends the turn.
- **Supplying tools:** `session/new` takes `mcpServers`. "All Agents **MUST** support the stdio transport, while HTTP and SSE transports are optional" (<https://agentclientprotocol.com/protocol/v1/session-setup>). So Dom could host an MCP server and hand it to the agent. The Claude and Codex adapters also support "MCP-over-ACP" (the client serves MCP over the same connection).
- **Disabling built-in tools:** **not part of the spec.** The security page says "The Agent runs with whatever permissions its process is given. ACP itself does not sandbox it" and "Permission requests are advisory: the Agent performs its own operations and is responsible for honoring the user's decision" (<https://agentclientprotocol.com/protocol/v1/security>). A client can refuse each permission request, but that is a policy outside the protocol, and it makes the agent waste turns. Each agent has its own switch (section 2).

## 2. The three agents

All three can run on the Pi's `aarch64` according to the official ACP registry (`https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json`, read 2026-11-23), except where noted.

### Claude (Claude Code via `claude-agent-acp`)

- **Install and start:** the npm package `claude-agent-acp` in the `agentclientprotocol` scope (registry id `claude-acp`, v0.110.0). It "implements an ACP agent by using the official Claude Agent SDK" (<https://github.com/agentclientprotocol/claude-agent-acp>). Install with npm, or use the standalone executable: releases attach Linux **arm64** archives (glibc and musl) holding the adapter and the Claude CLI, no Node needed. Dom would start the binary and speak ACP to it.
- **Auth:** a Claude login (subscription) or an API key. The adapter's README says `--full` smoke tests "need a Claude login". For headless use, the CLI documents `claude setup-token`: "Generate a long-lived OAuth token for CI and scripts … Requires a Claude subscription" (<https://code.claude.com/docs/en/cli-reference>). Whether the adapter honours that token is not documented in the README.
- **Built-in tools off:** the Agent SDK documents `tools: []`: "All built-ins are removed. Claude can only use your MCP tools", and deny rules that apply "even in bypassPermissions mode" (<https://platform.claude.com/docs/en/agent-sdk/custom-tools>, <https://platform.claude.com/docs/en/agent-sdk/permissions>). The CLI has a `--restricted` mode. **Whether the ACP adapter exposes `tools: []` is not documented**; it would need a source check or a trial.
- **System prompt:** the SDK's default is "a minimal prompt that covers tool calling", unlike `claude -p` which uses the full Claude Code prompt; a custom `system_prompt` is supported (<https://platform.claude.com/docs/en/agent-sdk/modifying-system-prompts>). What the *adapter* sends is not documented.
- **Latency:** not documented anywhere I found. Must be measured.

### Codex (OpenAI, via `codex-acp`)

- **Install and start:** `npx -y` on the `codex-acp` package in the `agentclientprotocol` npm scope or a global npm install; "The npm package includes a compatible OpenAI's `codex` package dependency", `CODEX_PATH` selects another binary (<https://github.com/agentclientprotocol/codex-acp>). The adapter "starts the Codex App Server". **Linux arm64 support of the bundled Codex binary is not stated** in the README; the registry lists only an `npx` distribution. Needs Node on the Pi, or a Mac on the LAN.
- **Auth:** "ChatGPT login", "API key via `CODEX_API_KEY` or `OPENAI_API_KEY`", or a custom gateway. Headless: `codex login --device-auth` (beta), and `NO_BROWSER=1` hides the browser method (<https://developers.openai.com/codex/auth>). For unattended use OpenAI documents copying `auth.json` to a trusted runner; Codex refreshes it itself (<https://developers.openai.com/codex/auth/ci-cd-auth>).
- **Built-in tools off:** `features.shell_tool` ("Enable command execution tools (stable; on by default)") can be set false; `INITIAL_AGENT_MODE=read-only`; `CODEX_CONFIG` is "JSON object merged into the Codex session config"; web search has its own setting (<https://developers.openai.com/codex/config-reference>, adapter README). No single "no tools" switch is documented; file reads (view_image) and web search are separate settings.
- **Latency and system prompt:** not documented.

### Gemini CLI / Antigravity (Google)

- **Gemini CLI is no longer an option for a subscription.** "Starting June 18, 2026, Gemini Code Assist IDE extensions stopped serving requests for the Gemini Code Assist for individuals, Google AI Pro, and Google AI Ultra tiers. This also applies to usage of Gemini CLI. … you can no longer use the Login with Google option to access the IDE extensions or Gemini CLI." (<https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals>). Gemini CLI itself still has `gemini --acp` (<https://geminicli.com/docs/cli/acp-mode/>) and can be used with a paid API key, which is API billing, not a subscription.
- **Antigravity CLI is Gemini CLI's successor** ("An important update: Transitioning Gemini CLI to Antigravity CLI", 2026-05-19, <https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/>). The ACP registry lists `antigravity-acp` v1.5.2 with a binary `agy_acp_server.par` for `linux-aarch64` and `darwin-aarch64`, so it can run on the Pi. A Google forum reply says `agy acp` "authenticates through its native `oauth-personal` flow" and that "outside of first-party IDE integrations, ACP sessions are scoped to the Gemini models included in your Google AI Pro plan" (<https://discuss.ai.google.dev/t/personal-app-using-the-official-agy-acp-binary-with-google-ai-pro-permitted/198889>).
- **Headless login and tool disabling:** I found no official page for either (the Antigravity docs URLs I tried returned 404 or an empty shell). **Unclear.** The forum poster says their client "refuses every tool permission request", which only works as a permission-request policy. Gemini CLI's policy engine has a `tools.core` allowlist, but that is for the old CLI.
- **Latency and system prompt:** not documented.

### What the Mac option adds

All three can run on a Mac on the LAN instead, where the owner is already signed in and browser logins work. Dom already reaches Claude and Codex agents on a Mac through the T3 bridge (`dom/t3/`) for coding tasks. A remote ACP agent would need a small stdio-over-network shim that does not exist; not worth it for v0.8.3.

## 3. Terms: may a personal bot run on the subscription?

### Claude

- Consumer terms (<https://www.anthropic.com/legal/consumer-terms>) forbid: "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise."
- Claude Code's legal page (<https://code.claude.com/docs/en/legal-and-compliance>): "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication." "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users." It adds: "Advertised usage limits for Pro, Max, and Ultra plans assume ordinary, individual usage of Claude Code and the Agent SDK." and it does not restrict "an end user [signing] in to the unmodified Claude Code binary with their own Claude subscription".
- The Agent SDK page repeats: "Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" (<https://platform.claude.com/docs/en/agent-sdk/overview>).
- **Reading:** the owner running an unmodified Claude Code interactively is allowed. A Telegram bot that sends every message through the owner's plan is "a bot, script" and "ordinary, individual usage" is doubtful. Processing friends' messages makes the "on behalf of their users" language closer. **Clear enough to say no for the bot; the exact edge for owner-triggered DM turns is not clear.**

### Codex / ChatGPT

- Codex auth page: two sign-in methods, "Sign in with ChatGPT for subscription access" and "Sign in with an API key for usage-based access". Both are supported by the CLI "for local work".
- CI/CD page: "The right way to authenticate automation is with an API key. Use this guide only if you specifically need to run the workflow as your Codex account." It calls the `auth.json` approach "an advanced workflow for enterprise and other trusted private automation", for "trusted private infrastructure" and "only one machine or serialized job stream", and warns "Do not use this workflow for public or open-source repositories" (<https://developers.openai.com/codex/auth/ci-cd-auth>).
- OpenAI's terms of use (<https://openai.com/policies/row-terms-of-use/>) forbid: "Automatically or programmatically extract data or Output". I did not find a clause saying a personal always-on bot on a ChatGPT plan is permitted or forbidden. **Unclear; the CI/CD page is the closest explicit permission, and it covers owner-run trusted automation, not serving friends.**

### Google (Antigravity)

- Antigravity terms (<https://antigravity.google/terms>): "Using third party software, tools, or services to access the Service (e.g. using OpenClaw with Antigravity OAuth) is a breach of this Agreement. Such actions may be grounds for suspension or termination of your Antigravity and/or Gemini CLI accounts." Gemini CLI's terms page says the same about "directly accessing the services powering Gemini CLI … using third-party software" (<https://geminicli.com/docs/resources/tos-privacy/>).
- A forum reply on a "personal app using the official `agy acp` binary" says it **is** permitted for "your own private, single-user interactive client … with the official, unmodified `agy acp` binary", but "Do not use the client for unattended background automation, multi-user serving, automated account rotation, or wrapping agy as a sub-agent inside another third-party coding agent loop" (<https://discuss.ai.google.dev/t/personal-app-using-the-official-agy-acp-binary-with-google-ai-pro-permitted/198889>, 2026-11-09). This is a community-forum answer, not the terms, and I could not verify who the replier is. By that reply Dom (unattended, serving other people, an agent loop around the agent) is outside the allowed use.

### Does it matter that friends' messages are processed?

Yes, in every case. Each provider's language is about *the account holder's own use*; Anthropic explicitly says "on behalf of their users", and Google excludes "multi-user serving". Friends' messages through the owner's plan makes the bot an intermediary. The plan already says friends' messages go to a subscription agent only if the research shows an acceptable retention policy; this research shows none, so **keep friends and groups off these providers**.

## 4. Data use and retention

| Provider and plan | Trains by default? | Retention | Zero data retention? |
| --- | --- | --- | --- |
| **Claude Free/Pro/Max/Ultra** | "We give you the choice to allow your data to be used to improve future Claude models … including when you use Claude Code from these accounts." | "5-year retention period" if training is allowed; "30-day retention period" if not (<https://code.claude.com/docs/en/data-usage>) | No. ZDR is "available to qualified accounts for Claude Code on Claude for Enterprise" only. Claude Code also keeps transcripts locally for 30 days. |
| **ChatGPT Free/Plus/Pro (Codex)** | "When you use our services for individuals (Free, Plus, Pro), we may use your content to train our models." Opt out with "Improve the model for everyone" off; that applies to "ChatGPT conversations and Codex tasks" (<https://help.openai.com/en/articles/5722486-how-your-data-is-used-to-improve-model-performance>) | Not found in what I read | No |
| **Google AI Pro/Ultra (Antigravity)** | "We use Interactions to evaluate, develop, and improve Google and Alphabet research, products, services and machine learning technologies. Google employees and contractors may access, view, review and use Interactions." A setting changes the preference (<https://antigravity.google/terms>) | Not found | No; "Even when your Telemetry is toggled off, Google still uses your data to provide the service" |

Options that could meet the ZDR rule: only API routes. Claude, OpenAI and Gemini each have API products, and Dom reaches them through OpenRouter's `zdr: true` today. None of the subscription routes meets zero retention. For the owner's own data, the plan allows an owner decision: opt out of training everywhere (Claude: <https://claude.ai/settings/data-privacy-controls>; ChatGPT: Settings → Data controls) and accept the remaining retention for owner-DM-only roles.

## 5. Fit with Dom

How Dom's turn works today (`dom/agent.py`, `dom/llm.py`): Dom calls an OpenAI-compatible `complete(messages, tools)`; if the reply has `tool_calls`, **Dom executes them itself** (scope checks, approvals) and loops; otherwise the reply text must be the JSON actions object, parsed with `parse_actions`. Fallback chains sit in `FallbackClient`.

- **JSON actions reply:** an ACP agent is just another text generator. The prompt includes the system text, history and the instruction to answer with the actions JSON; Dom's existing parser and its retry-then-fallback logic apply unchanged. Nothing in ACP prevents it. Whether the agent keeps to the format as reliably as Dom's current models is unmeasured.
- **Dom's own tools, without MCP (recommended):** keep Dom's loop as the owner of tool execution. The `acp` provider is a *text-only completion*: Dom sends the tool schemas inside the prompt and the agent answers either with the actions JSON or with a `{"tool_calls": [...]}` JSON that the provider converts to an OpenAI-style `tool_calls` reply. Scope checks, approval cards and the turn log stay in Dom. The agent has no tools at all (ideal), so no built-in-tool switch has to be perfect, only "do not use tools". Cost: one ACP prompt per loop step, so tool-heavy turns are slower. Drafting needs no tools. Escalation does: when the owner switches a turn to the bigger model, `dom/escalation.py` calls `provider.complete(messages, tools)` for the whole turn, tools included, so the text-only tool protocol must work there and needs its own test.
- **Dom's tools through MCP (alternative):** pass an MCP server in `session/new`. The agent runs the loop and calls back into Dom. This needs a per-turn authenticated MCP endpoint that knows the chat scope and approvals, and long approval waits inside an agent turn. More code and a bigger attack surface; **do not start here.**
- **"Only Dom's tools exposed":** with the text-only route nothing is exposed. With MCP, the built-in tool switch of each agent must be verified by a test that asks the agent to run a shell command and sees it fail; docs do not guarantee it.
- **Timeouts:** `session/prompt` takes as long as the agent takes. The provider needs a hard timeout, a `session/cancel` on expiry and a process restart when the agent hangs. The agent process should be long-lived (start-up cost unmeasured) with one new session per turn, no `session/load`, so no conversation state is kept in the agent between turns (Dom already supplies the history).
- **Spend cap and usage counting:** `UsageRecorder.record_response` reads `usage` and `cost` from an OpenAI-style response; `over_cap` sums recorded cost per day (and, per `config.daily_spend_cap_usd`'s description, the cap covers non-owner activity and desktop tasks). A subscription call has **no USD cost**, so recorded cost would be 0 and the cap would never bind. Recommend: record each ACP call as usage with tokens when the agent reports them (the Codex adapter lists "token usage" events; Claude's and Antigravity's are not documented) and cost 0, plus a **separate daily call budget** (`acp_daily_turns`, default small) enforced before the call, since a subscription's real limit is its own message allowance. An agent error that means "limit reached" must be treated like a 429: fall through to the next provider and, for a few minutes, skip that provider.

## 6. Recommendation

### Go or no-go

| Provider | Verdict | Why |
| --- | --- | --- |
| **Claude (claude-agent-acp)** | **No-go** | Consumer terms bar bots/scripts except with an API key; Anthropic says developers should use API keys. Dom already reaches Claude with an API key. |
| **Antigravity / Gemini CLI** | **No-go** | Terms call third-party access a breach; the forum reply excludes unattended and multi-user use; Gemini CLI login ended 2026-06-18; Google reviews and may train on interactions. |
| **Codex (codex-acp)** | **Conditional go, owner DM only, behind a switch** | OpenAI documents trusted private automation on a ChatGPT login and says API keys are preferred. Owner must opt out of training. The terms question for a Telegram bot is still unclear. |

The owner's actual goal is probably cost: the cheaper and cleaner route is API access through OpenRouter, which Dom already uses and which keeps zero data retention. If the goal is "use what I already pay for", Codex is the only candidate, with the caveat that OpenAI could object.

### Roles to start with (if Codex is approved)

1. **Owner-DM escalation** (`escalation` role): an occasional, owner-triggered, heavy-reasoning turn; the existing approval card already gates it.
2. **Drafting** (`drafting` role), owner-created plugin and skill drafts.
3. **Desktop tasks**: no; they run unattended, spend through the task cap, and involve other sites' content.

Not friends, not groups, not memory or reflection passes (those send notes about other people).

### Minimal design: an `acp` provider kind in `dom/llm.py`

- **Config:** `ProviderEndpoint` already has `base_url`, `model`, `api_key_env`. Add a provider kind: `kind = "acp"` (default `"openai"`) and, for `acp`, `command` (the adapter command line) and `model`. `base_url` is unused for it. W2's Providers tab lists it and its test call runs one real prompt. It can appear in `fallbacks` like any provider, so "escalation: acp, then OpenRouter" falls back without special code.
- **Code:** an `AcpClient` class beside `ChatClient` with the same surface: `available`, `complete(messages, tools, *, fallback, once, max_tokens, timeout)` returning an assistant message dict, `endpoint`, `address` (use `acp:<command name>`), `kind`. Inside:
  1. keep one long-lived adapter subprocess and an `asyncio.Lock` (one prompt at a time);
  2. `initialize` once; `session/new` per call with `mcpServers: []` and a temporary empty working directory;
  3. render `messages` (and the tool schemas, per section 5) into one prompt; send `session/prompt`; collect `agent_message_chunk` text from `session/update`; refuse every `session/request_permission`;
  4. enforce the timeout with `session/cancel`; restart the process on a crash or a hang;
  5. return `{"role": "assistant", "content": text}`, or `tool_calls` parsed from the text protocol.
- **Routing:** `routed_client` builds `AcpClient` when `endpoint.kind == "acp"`. `FallbackClient._complete` already falls through on `httpx` errors and `MissingProviderKey`; add one `AcpUnavailable` exception (adapter missing, not signed in, over its limit, timed out) to that `except` tuple and to `MODEL_FAILURES` in `dom/escalation.py`, which catches model errors itself. No other change to the callers.
- **Guards:** the provider kind may not be assigned to the `chat` role or to any chat other than the owner DM; this is enforced in code, where the provider is chosen, not in the prompt. `provider.zdr` does not apply; the Providers tab shows a clear "keeps data under the provider's consumer terms" note.
- **Tests:** a fake ACP agent (a script speaking JSON-RPC on stdio) covering success, a permission request that is refused, a timeout, a crash and restart, and fallback to the next provider; plus a test that a friend or group chat cannot route to an `acp` provider.

### Before building anything, measure (one spike, about half a day)

1. Start `codex-acp` on a Mac on the LAN with the owner's login and `features.shell_tool=false`, `INITIAL_AGENT_MODE=read-only`; check per-turn latency, whether it returns clean actions JSON, and whether a prompt that asks it to run a shell command fails.
2. Check `codex-acp` on the Pi (Node install and arm64 support), and headless `codex login --device-auth`.
3. Ask OpenAI support, in writing, whether an always-on personal Telegram bot on a ChatGPT plan is allowed. Keep the answer in the notes.

### Open questions for the owner

- Is the goal lower cost or "use my subscriptions"? If cost, an API route through OpenRouter may be enough and carries no terms risk.
- Is the owner willing to accept the unclear terms for Codex and the non-zero retention (with training opted out) for owner-DM escalation and drafting?
