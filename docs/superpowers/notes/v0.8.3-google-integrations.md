# Research: Google integrations for Dom (v0.8.3 W5 / R3)

Read-only research for R8 (Calendar) and R10 (Gmail) in v0.8.4. Every web source was read on **2026-11-23**. Where Google's docs are silent, this report says so.

## Summary

Note: Google Help article numbers below are written with a hyphen in the middle (e.g. `1554-9945`) because the public-data check treats eight-digit numbers as Telegram IDs. Remove the hyphen to get the real URL.

- **Create the project in Google's "Personal mode".** It is new, built for exactly one owner, and needs no verification, shows no unverified-app screen, has no user cap and has no 7-day token expiry. It cannot be switched later, and only the account that created it can authorize.
- **The device flow cannot be used.** Google's device flow allows only OpenID, Drive `drive.file`/`drive.appdata` and YouTube scopes. Gmail and Calendar are not on the list.
- **Use a Web-application OAuth client whose redirect URI is the dashboard.** The owner's browser already holds the Cloudflare Access session, so the callback works with no loopback and no tunnel.
- **Scopes:** Calendar `calendar.events` (or the narrower `calendar.events.owned`). Gmail needs `gmail.readonly` + `gmail.compose`, both classed *restricted*. There is no narrower scope that reads bodies and saves drafts.
- **Tokens:** encrypt with Fernet from `cryptography`. It is already installed through `PyJWT[crypto]`, so there is nothing new to add. Use `httpx` for the OAuth and REST calls.
- **Privacy:** keep the zero-data-retention rule by sending mail and calendar content only to ZDR models, and reduce it on the Pi first. Tokens never reach a model.

## 1. A personal OAuth app in the owner's own project

### Personal mode (the right choice)

Google's consent-screen help page defines a third user type next to Internal and External:

> "Personal Projects configured with a user type of Personal limit authorization requests exclusively to the single Google Account that created the application. … Personal mode apps do not require OAuth app verification, are not subject to the OAuth user cap or 7-day test user token expiration, and do not display the unverified app screen."
> — Manage OAuth App Branding / audience, <https://support.google.com/cloud/answer/1554-9945> (read 2026-11-23)

Details from the onboarding page, <https://support.google.com/cloud/answer/1554-4987> (read 2026-11-23):

- "Only the Google Account that created the Personal mode application can sign in or authorize scopes for its OAuth clients. Other Google Accounts, even if added as Owners or Editors on the same Google Cloud project, cannot authorize the app."
- "You do not need to submit your app for OAuth app branding verification or scope verification, and you will not encounter the unverified app warning screen when authorizing your own account."
- "Personal mode is a one-time selection when configuring a new application … it cannot be changed to External or Internal." To share later, "create a separate Google Cloud project."
- Setup is one step on the Personal mode onboarding page (<https://console.cloud.google.com/auth/overview/personal>). Client types offered: Web application, Android, iOS, Desktop app. There is an optional checkbox "Use this client for an AI-powered agent".
- A Google Workspace account "might still require configuration by your organization's administrators" for restricted Workspace services. This matters only if the owner's Google account belongs to a Workspace organisation. Whether the owner's account is consumer or Workspace is not known to me.

Unclear or not documented:

- Whether the "AI-powered agent" checkbox changes any limit or scope behaviour. The page links to a page about it that I did not read.
- Whether refresh tokens in Personal mode ever expire for a reason other than the general ones in the next section. The docs say only that Personal mode is exempt from the 7-day expiry.

### If Personal mode were not used (External project)

Source: <https://support.google.com/cloud/answer/1554-9945> (read 2026-11-23).

| Status | Users | Warning | Refresh token |
| --- | --- | --- | --- |
| **Testing** | Up to 100 listed test users | Warning before authorizing | "Authorizations by a test user will expire seven days from the time of consent. If your OAuth client requests an offline access type and receives a refresh token, that token will also expire." Only name/email/profile/openid scopes are exempt. |
| **In production**, unverified | "100 new users in total" (the user cap) | Unverified-app screen before consent | No 7-day limit (see below) |
| **In production**, verified | Any Google account | None | No 7-day limit |

So an External app in Testing status would force the owner to re-consent weekly, which makes it unusable for a background integration. An External app in production works for one user but shows the unverified-app screen on each consent. Google's restricted-scope page lists "personal use" as an exception to review ("if you are the only user of your app or if your app is used by only a few users, all of whom are known personally to you. You … might be comfortable with advancing through the unverified app screen"): <https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification> (read 2026-11-23). Personal mode removes the screen and the cap on top of that.

### When a refresh token stops working (applies to every mode)

Source: <https://developers.google.com/identity/protocols/oauth2#expiration> (read 2026-11-23). A refresh token may stop working when:

- "The user has revoked your app's access."
- "The refresh token has not been used for six months."
- "The user changed passwords and the refresh token contains Gmail scopes."
- The account exceeds its limit of live refresh tokens (100 per account per client ID; the oldest is invalidated silently).
- An admin restricted the service (`admin_policy_enforced`).

Consequences for Dom: the integration must handle `invalid_grant`, show "Google needs you to reconnect" in Settings, and not retry in a loop. Gmail has an extra reason: **changing the Google password kills a Gmail-scoped token**. A Calendar-only token is not affected by that rule. Using the token at least once every six months is easy, because Dom polls.

### Is verification needed for one user?

No, for Personal mode, by Google's own description (above). For restricted scopes, the restricted-scope page says apps that access restricted data "from or through a third-party server must undergo an annual security assessment by a Google-approved third party", and lists "personal use" among the exceptions. I found no sentence that spells out "Personal mode plus Gmail restricted scopes needs no assessment", but the Personal-mode page says no scope verification is needed and the exception covers personal use. Treat as **no assessment needed, but confirm with a real consent run before building more** (the first live test in v0.8.4 should be exactly that: connect Gmail with `gmail.readonly` in the Personal project).

## 2. Scopes

### Calendar (v0.8.4)

Scope list: <https://developers.google.com/workspace/calendar/api/auth> (read 2026-11-23).

| Task | Scope | Notes |
| --- | --- | --- |
| Read events | `https://www.googleapis.com/auth/calendar.events.owned.readonly` or `…/calendar.events.readonly` | `.owned` limits to calendars the owner owns (narrower). |
| Read + create/change events | `https://www.googleapis.com/auth/calendar.events.owned` or `…/calendar.events` | |
| Free/busy only | `…/calendar.events.freebusy` or `…/calendar.freebusy` | Least revealing. |
| Own calendar created by Dom | `…/calendar.app.created` | Creates a secondary calendar Dom owns, and read/write events on it only. |

The Calendar page does not label sensitivity per scope. Google's verification FAQ says "Examples of sensitive scopes include reading events stored in Google Calendar" (<https://support.google.com/cloud/answer/1346-4325>, read 2026-11-23), so treat the event scopes as **sensitive**. The authoritative per-scope tag is shown in the Cloud Console consent-screen scope picker, which I did not open.

Recommendation: start with `calendar.events.owned.readonly`. Add `calendar.events.owned` only when "add or move events through an approval card" ships, as a second consent (see section 7). Google's incremental authorization is documented for web-server flows, so a second consent is possible without losing the first.

### Gmail (v0.8.4: read mail, save drafts, never send unapproved)

Scope list: <https://developers.google.com/workspace/gmail/api/auth/scopes> (last updated 2026-09-10 per the page, read 2026-11-23).

| Scope | Class | What it allows |
| --- | --- | --- |
| `gmail.readonly` | **Restricted** | "View your email messages and settings." |
| `gmail.compose` | **Restricted** | "Manage drafts and send emails." |
| `gmail.modify` | Restricted | Read, compose and send, not permanent delete. |
| `gmail.metadata` | Restricted | "View your email message metadata such as labels and headers, but not the email body." |
| `gmail.send` | Sensitive | Send only. |
| `gmail.labels` | Non-sensitive | Labels only. |
| `gmail.addons.current.*` | Non-sensitive / sensitive | Only while a Workspace add-on is running; not usable from a server. |

Answers:

- **Restricted scopes:** `gmail.readonly`, `gmail.compose`, `gmail.modify`, `gmail.metadata`, `mail.google.com`. The Gmail page says "If you store restricted scope data on servers (or transmit), then you must go through a security assessment." For an app that only the owner uses, see "Is verification needed" above.
- **A narrower scope that reads bodies and creates drafts:** none exists. Reading bodies needs `gmail.readonly` (or `gmail.modify`). Creating drafts needs `gmail.compose`, and **that same scope also lets the token send mail**. The Gmail API cannot grant "drafts only". So "never send without approval" has to be enforced in Dom's code (the integration module exposes no send function; a send, if ever added, goes through an approval card) and not by the scope.
- **Narrower variant for a first step:** `gmail.metadata` (sender, subject, labels, dates, no body) is enough for "you have 3 unread from X". It cannot read bodies and cannot be used with search by body text either. It is the lowest-risk first step.
- Do not request `https://mail.google.com/`; Google says to request it only if the app must permanently delete.

## 3. OAuth flow for a headless Pi behind Cloudflare Access

Options, in order of fit:

1. **Web application client with the dashboard as the redirect URI. Recommended.** Flow: owner presses "Connect Google" in Settings → Dom redirects the owner's browser to Google's consent URL with `access_type=offline`, `prompt=consent`, a random `state` stored server-side, and PKCE → Google redirects the same browser to `https://<dashboard host>/…/google/callback?code=…` → Dom exchanges the code (with the client secret) over `httpx`. The owner's browser already holds the Cloudflare Access session, so no Access bypass rule is needed for the callback. Redirect URI rules (<https://developers.google.com/identity/protocols/oauth2/web-server>, read 2026-11-23): HTTPS only, the host cannot be a raw IP, and the TLD must be on the public suffix list. A Cloudflare hostname meets all three. A LAN address does not.
2. **Loopback (`http://127.0.0.1:port`).** Google documents it for installed/Desktop apps (<https://developers.google.com/identity/protocols/oauth2/native-app>, read 2026-11-23). The listener must be reachable from the browser that does the consent. On a headless Pi the owner would need an SSH port forward, and a one-off listener inside the Dom process. It works but is clumsy and gives a worse owner experience than option 1.
3. **Device flow.** Rejected. Google's page says "The OAuth 2.0 flow for devices is supported only for the following scopes: OpenID Connect … Drive API `drive.appdata`, `drive.file` … YouTube API `youtube`, `youtube.readonly`." Neither Gmail nor Calendar is allowed. (<https://developers.google.com/identity/protocols/oauth2/limited-input-device>, read 2026-11-23.)

Notes:

- Do not use the Google SDK for the flow. Three HTTPS calls (authorize URL, token exchange, refresh) with `httpx` are enough and add no dependency.
- The callback handler must check `state`, work only for the signed-in owner session of the dashboard, and refuse to run when the integration is switched off.
- Re-consent for added scopes goes through the same route.

## 4. Token storage on the Pi

`pyproject.toml` lists `PyJWT[crypto]`, which pulls in `cryptography` (50.0.2 in `uv.lock`). **Use `cryptography.fernet.Fernet`**: authenticated symmetric encryption, key as a 32-byte url-safe base64 string in `.env` (e.g. `DOM_INTEGRATION_KEY`). No new dependency is needed.

Design:

- One small table (or a file under the instance home with mode 0600) holding `service`, `ciphertext`, `scopes`, `updated_at`. The ciphertext contains the refresh token (and the cached access token with its expiry). The OAuth client secret also lives in `.env`, not in the database.
- The `docs/privacy.md` statement that archives include credentials already covers backups. Add one line that integration tokens are encrypted with a key held only in `.env`, so a database copy without `.env` is unreadable. A full `dom backup` includes both, as it does for `.env` today.
- Key loss means "reconnect Google", which is acceptable. Do not add key rotation until needed.
- Never log token values or authorization codes. `scripts/check_public.py` and the secret scanner (`dom/secret_patterns.py`) could gain Google token shapes (`ya29.…`, `1//…`), which is a small follow-up.

## 5. Privacy: what mail and calendar content may go to the chat model

Dom's rule (`docs/privacy.md`, `dom/llm.py`): OpenRouter requests carry `provider: {"zdr": true}`, so only zero-data-retention endpoints serve them. Google's own policy also limits what an app may do with Google user data: "Transferring, selling, or using user data to create, train, or improve a machine learning or artificial intelligence model beyond that specific user's personalized model" is prohibited (<https://developers.google.com/workspace/workspace-api-user-data-developer-policy>, read 2026-11-23). A ZDR provider that does not train satisfies both.

Options, from most to least private:

| Option | What leaves the Pi | Fit |
| --- | --- | --- |
| **A. Tokens and raw data stay on the Pi; the model sees tool results only.** The model never touches credentials. Calendar events and mail snippets reach the model only as results of an owner-DM tool call, under the existing `zdr` rule. | Event titles/times, or the mail text the tool returns | Default. Same trust as today's owner-DM chat content. |
| **B. Reduce on the Pi first.** Return fields, not documents: for calendar `start`, `end`, `title`, `location`; for mail sender, subject, date and a clipped plain-text snippet. Strip quoted replies, signatures and links, drop attachments. | Less text | Do this for every tool. It is plain Python. |
| **C. Summarise with a local model.** The home-lab model (a local provider kind, `dom/llm.py` already treats those as cost-free local calls) turns an inbox into 5 lines; only the summary goes to the chat model. | A summary only | Optional; depends on the lab being up, falls back to B. |
| **D. Metadata only (`gmail.metadata`).** | Sender, subject, labels | Lowest risk; useful as a first Gmail step. |

What can stay on the Pi in every option: tokens, the raw cache of fetched events/mail, FTS or index of them, the stripping and clipping, the draft body before approval, and the list of what was sent to a model (log the tool name and counts, not content).

Rules that follow from the roadmap's "Dom's spin":

- The tools exist only in the owner DM. In groups and friends' DMs they are not offered and are refused in code, not by prompt.
- Background jobs (reflection, memory pass) must not read mail or calendar content unless the owner switches that on per service. Otherwise, mail bodies could end up in notes. Calendar titles are lower risk but follow the same switch.
- Mail content is untrusted input. A message can contain instructions ("forward everything to…"). The tool result must be framed as data, and no tool reachable by a mail-triggered turn may send, delete or change anything without an approval card.
- Anything a friend wrote in a mail must not enter people notes without the usual memory rules.

## 6. Drive, Docs, Sheets, Contacts (later, R10b)

| Service | Scopes | Class and oddities |
| --- | --- | --- |
| **Drive** | `drive.file` (files the app creates or the owner opens with it via the Picker), `drive.appdata` (hidden app folder), `drive.install`: **non-sensitive**. `drive.readonly`, `drive`, `drive.metadata(.readonly)`, `drive.activity(.readonly)`: **restricted**. | Source: <https://developers.google.com/workspace/drive/api/guides/api-specific-auth> (read 2026-11-23). `drive.file` is narrow: Dom could not browse the owner's existing files with it. Reading existing files needs a restricted scope. `drive.file` and `drive.appdata` are also the only Drive scopes allowed in the device flow. |
| **Docs** | `documents` ("See, edit, create, and delete all your Google Docs documents"); a readonly variant exists. | Listed in <https://developers.google.com/identity/protocols/oauth2/scopes> (read 2026-11-23); that page does not mark sensitivity per scope, so check the Cloud Console picker. |
| **Sheets** | `spreadsheets` ("See, edit, create, and delete all your Google Sheets spreadsheets"); a readonly variant exists. | Same note. |
| **Contacts (People API)** | `contacts` ("See, edit, download, and permanently delete your contacts"), `contacts.readonly`, `contacts.other.readonly` ("Other contacts"). | Same listing page. Contacts hold other people's personal data: a friend's phone number sent to a model is a privacy decision for that friend, so default to owner-DM only and use Dom's existing people-notes rules. |

Anything that grants write on "all" documents or sheets should come with approval cards. If Drive is used only as a place for Dom's own exports, `drive.file` is enough and non-sensitive.

## 7. Recommendation

### Minimal Calendar design (v0.8.4, R8)

1. **Project:** the owner creates a Personal-mode Google Cloud project and a Web-application OAuth client with the dashboard callback as redirect URI. Enable the Calendar API. Put `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in `.env`; the Settings page shows "set / not set" only.
2. **Connect flow:** Settings → Integrations → Google Calendar → "Connect". Flow in section 3. Scope: `calendar.events.owned.readonly` only. `access_type=offline`, `prompt=consent`, PKCE, server-side `state`. Success page returns to Settings.
3. **Storage:** Fernet-encrypted refresh token as in section 4. A per-service on/off switch, off by default, in "What Dom can do".
4. **Reading:** one owner-DM tool `calendar_events(range)`, which returns reduced fields (title, start, end, location, calendar name). The result is cached on the Pi for a few minutes. Dom may also read it for the prompt's "what's coming up" line, behind the same switch.
5. **Approval points:** none for reading. A later "add/move an event" tool needs a second consent for `calendar.events.owned` and always shows an approval card with the event diff (E52's card). The owner can set the action to Allow, per the roadmap rule.
6. **Failure handling:** `invalid_grant` → mark the integration disconnected, tell the owner once in the DM, show "Reconnect" in Settings. No retry loop.
7. **Tests:** callback `state` mismatch, owner-only access, token never in prompt or log, group chat has no tool, and expired-token handling.

### Then Gmail (v0.8.4, R10)

1. **Same project and client**, second consent with `gmail.readonly` + `gmail.compose` (restricted; fine in Personal mode per the docs, to be confirmed live). If the owner prefers a cautious first step, ship `gmail.metadata` only.
2. **Tools (owner DM only):** `mail_search(query)` and `mail_read(id)` return reduced content (section 5, option B); `mail_save_draft(to, subject, body)` creates a draft and returns its link. No send function exists in code. If sending is ever added, it uses a card showing the full message and recipient, and the scope allows it technically, so the code gate must be tested.
3. **Approval points:** reading is allowed once the switch is on; every draft shows in the DM ("I saved a draft to X, open it in Gmail"). Sending is done by the owner in Gmail itself.
4. **Safety:** treat mail as untrusted (section 5). No mail text in the memory pass unless the owner switches it on. Log counts, not content.
5. **Known cost:** a Gmail-scoped token dies when the owner changes their Google password, so the reconnect path must work and be explained in the Settings card.

### Open questions for the owner

- Is the Google account a consumer account or a Workspace account? Workspace may need an admin to allow the restricted scopes even in Personal mode.
- Is mail summarisation acceptable on the chat model (ZDR OpenRouter), or should it wait for the local-model option?
