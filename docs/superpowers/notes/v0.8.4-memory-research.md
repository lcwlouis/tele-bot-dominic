# v0.8.4 W2 research: long-term memory in agent systems

Question (owner, 2026-11-25): how do other agent systems keep long-term memory, and what should Dom learn from them or do better? This feeds W2 (E75 journal archive, R13 source-tagged memory) in `docs/superpowers/plans/2026-11-25-v0.8.4.md`.

**How this was researched.** Dom's side was read from the code. The outside systems were researched with web search only, because no page-fetch tool was available. Facts below come from the search results, which quote official docs, papers and repos. Each cites its URL. A claim that came only from a third-party write-up is marked *(secondary)*. Nothing here was tried against a running system.

## 1. Dom today

**Files.** Everything is Markdown in the instance home, readable and editable by the owner.

| File | Limit | Written by | Read in |
|---|---|---|---|
| `memory/MEMORY.md` | 2200 chars | group memory passes only | the shared system prompt, every chat |
| `memory/people/<id>.md` | 1000 | group memory passes | any chat with that person present |
| `memory/chats/<id>.md` | 1000 | the pass for that chat | that chat only |
| `private/USER.md`, `NOTES.md` | 1375, 2200 | owner-DM pass | owner DM only |
| `memory/JOURNAL.md`, `private/JOURNAL.md` | none (`UNBOUNDED`) | nightly reflection | reflection only |

Limits are at `dom/home.py:19-26`, unbounded journals at `dom/home.py:30`. Dom never edits notes in a reply. A background pass does it (`dom/memory_pass.py:1-9`).

**Write path.**
- A pass runs per chat when a session ends, at most every 5 minutes (`dom/dispatch.py:91`, `dom/dispatch.py:441-461`).
- It reads up to 100 new messages plus the notes its scope may see, and asks the model for JSON `add`/`replace`/`remove` ops (`dom/memory_pass.py:32-36`, `:56-60`, `:128-180`).
- Which files exist for a pass depends on scope (`_offered`, `dom/memory_pass.py:192-204`). The owner DM gets USER and NOTES. A friend DM gets only its own chat notes. A group gets MEMORY, the notes of each speaker, and its own chat notes.
- When a note is over its limit, the write is refused and the model gets one retry to merge or drop older lines (`dom/memory_pass.py:161-175`).

**Journal.**
- Reflection writes one entry a day (`dom/reflection.py:178-217`) and reads the last 3 entries back (`dom/reflection.py:170-175`).
- `append_journal` keeps the last 30 entries and drops the rest (`dom/home.py:242-250`, the slice at `:249`).
- Journals are never in chat prompts. Their only searchable copy is the live file.

**Prompt.**
- Shared prefix (system message): frame, SOUL, MEMORY.md, HABITS.md, skills (`dom/prompt.py:233-236`).
- Per-chat notes go in the user message after that prefix, before the chat window (`dom/prompt.py:94-109`, `:252-256`).
- MEMORY.md and per-chat notes are snapshotted and refreshed hourly (`dom/prompt.py:16-17`, `:144-200`). So a MEMORY.md rewrite costs one prefix miss for every chat, at most once an hour.

**Search.**
- `search_history` is FTS5 over messages. It orders by `rank` (BM25) only, with no recency (`dom/store/store.py:2681-2704`).
- Non-owner chats search only themselves. The owner DM searches every chat.
- Dashboard global search covers memory files, but only `memory/*.md`, `memory/people`, `memory/chats` and `private/*.md` (`dom/global_search.py:61-66`).

### Gaps

1. **The journal is lost, not archived.** After 30 entries, older ones are deleted. It is 30 entries, not 30 days: a skipped day stretches the window, and nothing summarises what falls off (`dom/home.py:249`).
2. **Facts carry no date and no source.**
   - Notes are free-text bullets. "Starting a new job" cannot be told from last year's news.
   - `replace` overwrites, so the old fact is gone, with no history.
   - The model cannot tell a stale plan from a current one.
3. **Privacy is enforced by prompt text, not structure.**
   - `GROUP_RULES` (`dom/memory_pass.py:38`) asks the model to keep personal things out of `people/<id>.md`.
   - Once a fact is in that file, `_read_chat_notes` shows it in every chat where the person is a participant (`dom/prompt.py:105-108`).
   - MEMORY.md is written from group content and read everywhere (`dom/memory_pass.py:203`, `dom/prompt.py:117`). This is the R13 problem.
4. **Retrieval of old things is flat.** BM25 treats a two-year-old and a two-day-old match the same, and there is no "this matters" signal. Journals and archives are outside `search_history` and `global_search`.
5. **Consolidation is capacity-driven only.** Merging happens when a write is refused, not on a schedule. Nothing links a day's entry to a month's story.

## 2. How other systems do it

### Comparison

| System | Store | Consolidation | Aging | Retrieval | Contradiction and time | Source and privacy | User inspect/edit |
|---|---|---|---|---|---|---|---|
| **Letta / MemGPT** | In-context *core* memory blocks with char limits; *recall* (full message history, searchable); *archival* (indexed passages) | Agent edits its own blocks; old messages compacted into a summary; optional *sleep-time* agent rewrites blocks in the background | No decay. Core is size-bounded; the rest stays | `conversation_search`, `archival_memory_search` as tools | The agent rewrites blocks; no formal validity | Per-agent state; blocks can be shared between agents | Blocks readable and editable through the API |
| **mem0** | Extracted fact memories (vector; optional graph variant "Mem0g") | Per message pair: extract candidates, compare with similar memories, choose ADD / UPDATE / DELETE / NOOP | No decay; update and delete are the aging | Similarity search | Contradiction handled by UPDATE/DELETE at write time | Scoped by user/agent ids *(not verified here)* | API and dashboard *(not verified here)* |
| **Zep / Graphiti** | Temporal knowledge graph: entities, fact edges, raw episodes | Ingest-time extraction; LLM checks new edges against similar old ones | Old facts are invalidated, not deleted | Hybrid: semantic, BM25 and graph traversal | Each edge has `valid_at`, `invalid_at`, `created_at`/`expired_at`; relative dates resolved against the episode time | Episodes keep provenance; per-user graphs | Query API; graph database needed |
| **LangMem / LangGraph** | Semantic (facts), episodic (past interactions as examples), procedural (rules and prompts) in a store | Background memory manager extracts, consolidates and updates between conversations; or hot-path tools during the reply; procedural memory via prompt optimisation | Not described in what I read | Store search by namespace | Manager updates or merges existing items | Namespaces per user/team | Store API |
| **ChatGPT** | Saved memories (list) plus "chat history" reference; improved memory has a running summary | Platform-managed; chat-history detail shifts as it decides what is useful | Saved memories kept until deleted; history details change | Platform-internal | Not documented | Per user; Temporary Chat neither reads nor writes | Manage memories in settings; ask it to forget; toggles; deleting a memory leaves old chats, which must be deleted separately |
| **Claude memory tool** | Files under a virtual `/memories`, stored by the developer | The model reads and writes files itself | Developer-defined | Model lists and views files | Model rewrites files | Developer maps `/memories` to per-user storage | Files are the developer's own, readable by design |
| **Claude Code** | `CLAUDE.md` instructions, plus auto-memory `MEMORY.md` with topic files | Model writes auto-memory; user edits | Index loads only first 200 lines or 25 KB; topic files on demand | Index at session start; topics read when needed | Model rewrites | Per project, per user | Plain Markdown files |
| **Generative Agents** | Memory stream of natural-language observations | Reflections: higher-level inferences stored back into the stream | Recency by exponential decay over hours | Score = relevance + recency + importance (LLM-rated integer) | None; later reflections can supersede | Single-agent world | Not a product |
| **A-MEM** | Notes with keywords, tags and links (Zettelkasten) | On a new note: link to related notes and *evolve* old notes' descriptions | None in the paper | Embedding filter, then link traversal | Evolution rewrites old notes | Not a focus | Not a focus |
| **Companion projects** (SillyTavern and extensions, companion-engine, Smrti) | Chat log, summaries, vector store, extracted facts | Periodic summaries; some extensions extract long-term facts | Some add decay: forgetting curve, short-term importance that decays and long-term that accumulates | Vector search on past messages | Summaries can drift or invent detail | Mostly one user | Often editable text |
| **Dom (now)** | Bounded Markdown notes + daily journal + FTS5 messages | Background pass on session end; overflow merge | Journal: 30 entries then deleted | `search_history` BM25 | None: replace overwrites | Per-scope files; privacy is prompt-enforced | Files and dashboard memory page |

### What the field agrees on

- **Write in the background, not in the reply.** Letta's sleep-time agents, LangMem's background manager and Dom's memory pass share this design. Sleep-time work is mostly consolidation, so cheaper models do it well (a Letta forum [community guide](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154), *secondary*). Dom already does this.
- **Keep a small always-loaded core and a large searchable archive.** Letta's core/recall/archival and Claude Code's 200-line index plus on-demand topic files both do this. Dom has the core (MEMORY.md and per-chat notes) and a message archive (FTS5). It lacks an archive for its own written memory, which is the journal.
- **Supersede, do not erase.** Zep keeps old facts with an end time. ChatGPT keeps deleted-memory logs for up to 30 days. A 2026 survey flags that many forgetting systems never record who authorised a decay or how to reverse it ([Always-On Agents](https://arxiv.org/pdf/2606.30306)). Dom's `replace` and `remove` do not keep the old text.
- **Forgetting is mostly lowered retrievability.** Systems that decay do it by ranking, not deleting ([Memory for Autonomous LLM Agents](https://arxiv.org/abs/2603.07670)).
- **Summaries drift.** SillyTavern's own guidance warns that summaries lose details or hallucinate ([guide](https://www.roborhythms.com/sillytavern-memory/), *secondary*). Keep raw sources next to every summary.

## 3. Recommendations for v0.8.4

Ranked by value over complexity. All keep plain files, no new service, and no embeddings.

### 1. Journal archive (E75), small and high value

Change `append_journal` (`dom/home.py:242-250`) so it moves entries older than 30 days into `memory/journal/YYYY-MM.md` (and `private/journal/YYYY-MM.md`) instead of dropping them. The cutoff should be by date, not by the last 30 entries, so a gap in days does not keep stale entries.

- Dom keeps reading the last 3 entries for reflection (`dom/reflection.py:171`); nothing about his daily loop changes.
- The archive is not in any prompt and not size-bounded. It follows the `UNBOUNDED` pattern (`dom/home.py:30`). The memory edit and export code needs the new paths.
- Add the two folders to `_memory_paths` (`dom/global_search.py:63`) so the dashboard finds them. Decide whether Dom's own tool may search the public archive: yes for `memory/journal/`, never for `private/journal/` outside the owner DM. The private boundary is already `Home.allow_private` (`dom/home.py:79`).
- Add a one-time migration that does not delete the current file on failure: write the archive first, then trim.

### 2. Monthly summary, small to medium

When a month closes, one cheap-model call reads that month's archive file and writes a summary of at most about 600 characters at the top of the file (`# 2026-11 — summary`). The raw entries stay below it, so a drifting summary can always be checked against its source.

- **Where it goes in long-term memory.** Put one line per month in MEMORY.md, keep only the last 6, and roll older ones into one "earlier" line. The archive keeps the full text. Do not let the summaries fill the 2200-character file.
- **Private journal.** Its summary goes to `private/NOTES.md`, never MEMORY.md. MEMORY.md is read by every chat.
- **Cache.** MEMORY.md is in the shared prefix. Write it once a month, in the overnight job, and rely on the existing hourly snapshot (`dom/prompt.py:163-170`). That costs one prefix miss for all chats a month, which is negligible. Do not rewrite MEMORY.md as part of each day's reflection.
- Use the existing memory-pass write path (`Home.memory_write`) so limits and locking still apply.

### 3. Dated facts and supersede-not-delete, medium (this is "fact validity over time")

Do not build a graph. Zep's `valid_at`/`invalid_at` idea ([paper](https://arxiv.org/abs/2501.13956)) can be had with plain text.

- **Date on write.** Ask the memory pass to end each bullet with `(as of YYYY-MM)`, or `(until YYYY-MM-DD)` for plans. The model resolves "next week" using the message dates, as Graphiti does with its reference timestamp ([Zep blog](https://blog.getzep.com/beyond-static-knowledge-graphs/)).
- **Keep what was replaced.** On `replace` or `remove`, Home appends the old line, with the date it was superseded, to a sibling file such as `memory/people/<id>.former.md`. It is not in the prompt, not size-bounded, searchable, and the owner can read it. This is the cheap version of Zep's invalidation, and it makes a wrong merge recoverable.
- **Code does the expiry.** A small sweep in the memory pass moves lines whose `until` date has passed into the former file. The model should not have to remember to do it.
- This adds characters to every bullet, so raise the people and chat limits a little (for example 1000 to 1400), or measure the limit on text with the tag stripped. Decide which when W2 is built.

### 4. Source tagging (R13), medium, high trust value

Put the source in the bullet, in a form the owner can read and edit:

```
- Works as a nurse (as of 2026-11) {chat -100123}
- Hates surprises {any}
```

- `{chat ID}` means "told in that chat, use only where its members were present". `{any}` means "the person would say this anywhere". The memory pass (`dom/memory_pass.py:38`, the group rules) already tries to make that call. Now the call is stored.
- **Filter in code, not in the prompt.** `_read_chat_notes` (`dom/prompt.py:94-109`) keeps lines tagged `{chat X}` only when X is the current chat, or when the current chat's known members were all in X. It strips the tags before rendering. Because notes sit in the per-chat user message, not the shared prefix, the filter does not touch the prefix cache (`dom/prompt.py:252-256`).
- **Legacy lines have no tag.** Treat them as `{any}`, which is how they behave today, so no migration is needed. The pass can add tags as it rewrites lines.
- **MEMORY.md:** every line is read by every chat, so lines written from a group pass must be `{any}` or go to the chat's own notes. Reject a MEMORY.md write with a `{chat}` tag in `Home.memory_write`.
- **Friend DMs and the owner DM** already write into scoped files, so they need no tag.
- Test with an eval: a fact told in group A must not surface in group B. The repo already has a leak-check eval plan (`docs/superpowers/plans/2026-11-19-leak-check-eval.md`).

### 5. Recency in search, small

Do not use an LLM importance score per message. Generative Agents rate every memory for importance ([paper](https://arxiv.org/abs/2304.03442)), which would cost a model call per message on a Pi-hosted bot.

- Pull the top 30 BM25 hits from `search_history` (`dom/store/store.py:2702`), then re-rank in Python: `score = bm25_rank_position + recency_penalty`, with a soft half-life of about 60 days. Skip the penalty when the query contains a date or phrases like "last year". Recency is the one part of the Generative Agents score that is cheap.
- **Importance without a model call.** Give pinned or repeated facts a free signal. A line the owner edited by hand, or one the pass re-confirms in a later session, is marked `!` and exempt from the `until` sweep and from merging. This is the cheap analogue of importance.
- Search the archive and former files too, labelled by month, so "what did we say about that trip in spring?" reaches summaries first and raw entries second.

### 6. Defer

- A sleep-time pass that reorganises notes on its own (Letta, A-MEM). Wait until dated facts and `.former` files exist, so there is a record to undo from.
- Reflection that makes new "insight" facts (Generative Agents). Dom's daily journal already plays this role; its facts should come from the notes, not the other way round.

## 4. What not to copy

- **Vector DB or graph DB.** Zep, mem0 and A-MEM need embeddings or a graph store. On a Pi with per-chat files of 1000 characters, BM25 plus dates covers the need. Revisit when an archive has thousands of entries and search misses.
- **Letta-style self-editing in the reply turn.** Dom's reply path is cache-sensitive and in character. Background-only writes (today's design) keep the reply fast and the prefix stable. Letta itself moved memory work to sleep-time agents to avoid blocking the main agent ([blog](https://letta.com/blog/sleep-time-compute)).
- **ChatGPT's opaque "improved memory" summary.** The owner can't see what is in it, and deleting a memory doesn't remove its traces from history ([OpenAI help](https://openai.com/index/memory-and-new-controls-for-chatgpt/)). Dom's files are the whole point.
- **Silent LLM rewriting of old notes (A-MEM "evolution", mem0 DELETE).** The paper's gain comes from rewriting old memory when new memory arrives. Dom wants every rewrite to be reversible, so any rewrite goes to a `.former` file first.
- **Numeric decay that deletes.** Decay constants like a 29-day half-life are from one benchmark-tuned system ([arXiv 2605.08538](https://arxiv.org/pdf/2605.08538)). Use recency only to rank, never to delete.
- **Prompt-only privacy.** A rule the model is asked to follow is not a boundary. R13 should be enforced in `Home` and the prompt builder.

## 5. Suggested order for W2

1. Archive and date-based trim (rec. 1), with the global-search paths.
2. Dated bullets plus `.former` (rec. 3), because the source tags need the same line format.
3. Source tags and the prompt filter (rec. 4), with the leak eval.
4. Monthly summary (rec. 2), once the archive exists.
5. Recency re-rank (rec. 5), last, because it is the most tunable.
