# Phase 7 — Polish and release — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** someone other than the owner can set Dom up from the README on a fresh Raspberry Pi; operators get a health check and a one-command service install; CI runs the tests and blocks personal data; the dashboard gets its visual pass.

**Spec:** roadmap `docs/superpowers/plans/2026-11-19-roadmap-phases-3-7.md` (Phase 7, D11, "Publishing").

## Global Constraints

- All earlier Global Constraints hold. Public repo: no real IDs, names, chat titles, LAN addresses or domains anywhere. No network in unit tests.
- Commands that change the system (`install-service`, `desktop-setup`) print what they will do and need `--yes` to act.

## Task 1: `dom doctor`

**Files:** `dom/doctor.py`, `dom/cli.py`, tests.

- `dom doctor <home> [--online]` prints one line per check, `ok`, `warn` or `fail`, with a fix hint; exit code 1 if any `fail`.
- Offline checks (always): config parses; required secrets present for the configured models (names only, never values); `owner_id` set (else: how to claim); timezone valid; SOUL.md present and under its limit; memory files within limits; `state.db` opens and its migration version matches the code; backups folder has an archive newer than 36 h (warn otherwise); free disk ≥ 2 GB under the home (warn) and ≥ 500 MB (fail); `[web]` auth settings consistent (reuse the server's validation); `[desktop]` settings consistent and, in local mode, `docker` present and `lan_probes` set; plugins: `bwrap` present and the sandbox self-test result.
- `--online` checks: Telegram `getMe` (token valid) and `getMyCommands`; the bot's privacy mode (`can_read_all_group_messages`), with a hint for BotFather; each configured model endpoint answers a minimal request (chat models: `/models` or a 1-token completion; triage: one Jev call); OpenRouter key spend left if the API reports it.
- Tests: each offline check with good and bad fixtures; secrets never printed; exit code; online checks with mocked HTTP.
- Commit: `feat(cli): dom doctor`.

## Task 2: `dom install-service`

**Files:** `dom/service.py`, `dom/cli.py`, `docs/deploy-pi.md`, tests.

- `dom install-service <home> [--yes]` writes systemd **user** units — `dom.service` (as running on the reference Pi: `MemoryHigh=500M`, `MemoryMax=700M`, `Restart=on-failure`, `RestartSec=15`, `Nice=5`, `WorkingDirectory` = the app directory, `ExecStart=<venv python> -m dom run <home>`), `dom-backup.service` + `dom-backup.timer` (04:00, `Persistent=true`, idle I/O) — into `~/.config/systemd/user/`, runs `daemon-reload`, enables them, and prints the `loginctl enable-linger` command if linger is off (it doesn't run sudo).
- Without `--yes` it prints the unit files and the commands instead.
- Refuses if the units exist and differ, unless `--force`.
- `docs/deploy-pi.md`: the release layout (`releases/<sha>`, `app` symlink, rollback), the update procedure (`git archive`/`git pull` + `uv sync --frozen --no-dev` + backup + switch), persistent journal on Raspberry Pi OS, a power/thermal logging timer, and where logs are.
- Tests: unit file content; dry run prints and writes nothing; refuses differing units; `--force`.
- Commit: `feat(cli): dom install-service`.

## Task 3: setup guide and docs index

**Files:** `README.md`, `docs/setup.md`, `docs/configuration.md`, `docs/privacy.md`.

- `docs/setup.md`: from zero to first message — create the bot in BotFather (privacy mode, bot-to-bot), Raspberry Pi prerequisites (64-bit OS, `uv`, optional `bubblewrap`, optional Docker), `dom init`, `.env`, choose models (OpenRouter defaults; a self-hosted OpenAI-compatible server), `dom doctor`, `dom install-service`, `/claim`, approving groups, the owner commands, the dashboard (Cloudflare Access), the desktop (optional, with `desktop-setup` and the image pull warning), plugins (optional).
- `docs/configuration.md`: every config key with default and meaning, generated by a small script `scripts/config_reference.py` from the config model so it can't drift; a test fails when the generated file is stale.
- `docs/privacy.md`: what is stored where, the scopes, what leaves the machine (model providers, search, Jev), the leak check, plugins and desktop isolation.
- README: short, links to the three docs; no claims beyond what works.
- Commit: `docs: setup guide, configuration reference and privacy notes`.

## Task 4: CI and the personal-data guard

**Files:** `.github/workflows/ci.yml`, `scripts/check_public.py`, tests.

- CI on push and pull request: Ubuntu, Python 3.12 via `uv`, `uv sync --frozen`, `uv run pytest -q`. A second job on `ubuntu-latest` installs `bubblewrap` and runs the plugin sandbox integration tests (they need Linux + bwrap; mark expected skips explicitly if unprivileged user namespaces are unavailable on the runner).
- `scripts/check_public.py`: scans tracked files (excluding vendored assets, `uv.lock` and binary files) and fails on: Telegram-ID-like numbers (8–12 digits) outside an allowlist of known test values; Telegram handles outside an allowlist; private IPv4 addresses outside documentation ranges (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`) and the generic CIDR ranges the firewall code uses; email addresses other than `example.*`, GitHub noreply and the vendored licence authors. The allowlists live in `scripts/check_public.toml`. Run in CI; also runnable locally (`uv run python scripts/check_public.py`).
- Tests for the scanner with planted examples.
- Commit: `ci: tests, sandbox tests and a personal-data guard`.
