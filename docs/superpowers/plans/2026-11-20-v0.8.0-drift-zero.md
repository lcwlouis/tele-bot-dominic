## Workstreams

### W1 Reply reliability (E1, E2)

- Diagnose the malformed finals from the homelab `default` model with real recorded
  outputs (6 of 10 recent turns, 2 dropped as "Stayed quiet"). Fix the cause: likely
  `response_format`/guided JSON on the vLLM endpoint, the final-answer parser, or tool-call
  formatting. Verify against the real endpoint, not mocks.
- Never drop silently: after the correction retry fails, fall back to the fallback model
  for the final answer; if that also fails, log loudly and tell the owner in their DM
  (owner DM turns) instead of staying quiet.
- Reactions: the prompt lists the emoji Telegram allows for bot reactions, and the action
  validator maps anything else to null before calling the API.
- Reflection: the `mood` field is constrained (Jev `choice` or a fixed list) so it is
  never blank.
- Seen reaction (E2): while a chat is online, when a turn ends with no bubbles and no
  reaction, Dom reacts 👀 to the newest message he read. Never while asleep/offline,
  never in chats where reactions are not allowed, at most one per batch. Off switch in
  `config.toml` (`presence.seen_reaction`, default on).

### W2 Instance-home clean-up (E3)

- Fix the importer bug that put "Habits and Style: …" text into `preferred_name`.
- One supervised pass over the instance home: keep real facts (including ones the memory
  pass merged in this week), drop migration boilerplate, the V2 journal entry and
  security-classification banners, re-key `handle_*` people to Telegram user IDs once
  known, trim every note under its cap. The owner reviews `private/USER.md` before save.
- `dom doctor` reports no warnings afterwards.

### W3 Skills in chat (E4)

- `skills_list` and `skill_view` in every scope's tool table (skills are public-scope
  content). Only name + description of each skill sit in the prompt.
- `skill_manage` (create/update) stays a proposal the owner approves (roadmap 3/5.7).
- Desktop worker keeps its existing skill access through the same module.

### W4 Dashboard (E5 and spec §12)

- Chats panel: edit each of the per-chat sliders, with "reset to default"; values go
  through the same validation as `/preset`.
- Memory import: upload a `.txt`/`.md` file and pick the service; it runs the same
  `MemoryImport` path as Telegram `/import`.
- Approvals: pending groups and stranger DMs are listed with Approve / Ignore
  (spec §12 "approvals: groups").

### W5 `/update`, releases and devices (E6)

- `/update` (owner DM only): shows the newest `vX.Y.Z` tag on the configured public repo
  with its changelog section; on confirm, Dom deploys it through the existing release
  steps (fetch tag, unpack, `uv sync --frozen`, backup, repoint `app`, restart), and
  rolls back to the previous release if the new one is not healthy within a deadline.
  Only tags; never an arbitrary ref.
- Deploys keep the current and previous release only.
- `find_devices` (owner DM, read-only): mDNS/ARP discovery of the LAN with names and
  addresses. A changed address for a configured host becomes a config proposal the owner
  approves. Configured hosts may be given by `.local` name instead of a fixed IP.

### W6 Ops and branch (E7)

- Remove the stopped V2 containers and their images on the Pi (pull/remove one at a
  time; the Pi is memory-constrained).
- Fast-forward `main` to `dom-core`; new work lands on `main` through PRs; delete
  `dom-core` once nothing points at it. Personal-data scan before every push.
- CHANGELOG `Unreleased` lists everything since v0.7.0.

### W8 Release gate (E8)

1. Both reviewers get this file, the spec, the roadmap and the code, and read the Pi's
   state read-only. Each lists any decision that is missing, narrowed or unverified.
2. Fix or get an owner re-decision for every finding; record re-decisions here.
3. Repeat until both report zero. Then tag `v0.8.0` and deploy it with `/update`.
