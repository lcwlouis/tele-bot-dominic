## Workstreams

### W1 Reply reliability (E1, E2)

- Diagnose the malformed finals from the homelab `default` model with real recorded
  outputs (6 of 10 recent turns, 2 dropped as "Stayed quiet"). Fix the cause: likely
  `response_format`/guided JSON on the vLLM endpoint, the final-answer parser, or tool-call
  formatting. Verify against the real endpoint, not mocks.
- Never drop silently: after the correction retry fails, fall back to the fallback model
  for the final answer; if that also fails, log loudly and tell the owner in their DM
  (owner DM turns) instead of staying quiet.
- Reactions: the prompt lists the emoji Telegram allows for bot reactions, and the action
  validator maps anything else to null before calling the API.
- Reflection: the `mood` field is constrained (Jev `choice` or a fixed list) so it is
  never blank.
- Seen reaction (E2): while a chat is online, when a turn ends with no bubbles and no
  reaction, Dom reacts 👀 to the newest message he read. Never while asleep/offline,
  never in chats where reactions are not allowed, at most one per batch. Off switch in
  `config.toml` (`presence.seen_reaction`, default on).

### W9 More than one desktop container (E12)

- Dom can run several desktop containers at once, one per project or task, on any
  configured host (`local` Pi, `remote` hosts).
- Resources first: each host has a container limit and a memory floor. Before starting a
  container Dom checks the host's free memory and refuses (and says so) rather than
  starting one that would breach the floor. Idle containers stop after the idle timeout.
  Defaults: the Pi allows one; other hosts are owner-configured. The M1 keeps 16 GB free
  for its other user.
- Handoffs, screenshots and the dashboard viewer name which container they belong to.

### W13 Planned self-directed work (E20)

- In the nightly daydream Dom may plan up to three small tasks of his own (research, tidying his notes, practising a skill). Each has a goal, the tools it will use, the sites or areas it will touch, and a time and step budget.
- The plan is sent to the owner's DM and shown on the dashboard, each task with a Cancel button. A task starts no sooner than a set delay after it was announced, and only while Dom is awake and idle. Results and screenshots go to the dashboard.
- Self-directed tasks run only in the desktop sandbox, and only when a network guard that blocks private and LAN addresses from that container is verified in place. Otherwise they are refused. No logins, accounts, posting, purchases, scanning or form submissions beyond search.

As built (2026-11-21), with the details that differ from the lines above and why:

- **No "tidy his notes" tasks.** Dom's notes live in `DOM_HOME` on the host, and self-directed work never gets host access. Tasks are research on named sites (practice in the sandbox was dropped in the second hardening round below); note-keeping stays with the nightly reflection.
- **Planning is its own daily job** (`self-work`, `dom/selfwork.py`) in the same hour before sleep, registered right after `reflection`, so the reflection code is untouched. It reads only public content (soul, public journal, earlier task goals).
- **Local desktop hosts only**, in a dedicated `self-work` container whose browser profile is deleted before every task. Dom cannot reset a remote host's profile or check its firewall, and the default container holds the owner's logins.
- **The blocking rule is the existing `DOM-DESKTOP` firewall** installed by `sudo dom desktop-setup <home> --yes`; local containers were already LAN-blocked and checked by a probe container at every start, so no new rule or command was needed. W13 adds a second check from inside the actual sandbox before each task (public control reachable; `lan_probes`, the Docker host's LAN address and the gateway time out; sampled private addresses do not answer). The last result is stored and `dom doctor` reports it. Owner-initiated tasks are unchanged.
- **Code-enforced limits beyond the brief:** only the planned tools (never `handoff`, skills or skill proposals), the browser held to the planned sites (an off-plan page is closed, or the task stops), short search text only for `fill`, and the step and time budgets (time counts from when the container is up and the guard has passed).
- **Hardened after the security review (2026-11-21):** the offline wrapper uses `/usr/bin/unshare ... /bin/sh -c` and the guard checks that exact wrapper has no network; a task that changes a shell startup file is stopped (absolute paths alone do not stop a bash function named `/usr/bin/unshare`, and the sandbox's bash API decides itself which startup files it reads, so Dom watches the files instead); files only under `/tmp` and the outbox; strict URL parsing with ports 80/443 only; no public-suffix sites (a built-in list of common multi-tenant suffixes plus country second levels, instead of a Public Suffix List dependency: plans name a few sites and the LAN guard stays the backstop); `press` and `click` limited so the only form is a search, failing closed when the element list cannot tell a link from a button; a plan is runnable only after its DM was delivered (start time set afterwards, so no migration change); self-directed tasks run only while every other local container is stopped, enforced in the host's admission check (ICC is not turned off: it needs the bridge recreated); a timeout counts as proof only for targets that answer from the host, in the guard and in every container's startup check; the DM summary is labelled as web content with links removed.
- **Second hardening round (2026-11-21):** self-directed tasks are browser research only. `run_shell` and `run_python` are removed (planner, validator and worker), because they share the user, files, Chromium socket and X display with the browser and could drive it past every browser rule; with them gone, the offline wrapper, its guard check and the startup-file watch protected nothing and were deleted (owner tasks never used the wrapper). `click` takes only an index that the freshly read element list (`tag`, `role`, `type`, `href`, as the Pi's sandbox returns them) shows as a link to a web address; `fill` takes one simple selector naming a search field, only when the page shows a search box (the element list does not say which element a selector names); Enter only right after a search fill. At most four sites per task, always shown in full; the suffix list gained `me.uk`, `ed.jp`, `eu.org`, `uk.com`, S3 region hosts and `blogspot.*`, and `go.to` is allowed again. The DM summary strips any `scheme://`, IDN and punycode domains and user mentions. A start the host refuses (another container started first) puts the task back to `planned`.
- **Default on** (`[self_work] enabled = true`): the owner approved the feature, and it is inert unless a local desktop host is configured, which already requires the firewall. Tasks wait `delay_hours` (default 3) after the announcement and expire after a day.

### W17 Cache-friendly prompt and turn timing (owner, 2026-11-21: "be careful how we compress our chat memory since that'll invalidate the cached context")

- The homelab model caches prompt prefixes in blocks (816 tokens observed). The system prefix is stable, but the chat window slides by one message per turn once it is full, so everything after it is recomputed every turn, and memory passes rewrite notes at other times.
- Trim the window in chunks instead of one message at a time, so its start stays fixed between trims, and run the memory pass at the trim so both invalidations happen together.
- Record each step's duration in the turn log (triage, each model call, tools, typing), so reply latency can be attributed to real causes before any further speed change.

As built (W16): the `task_mode` tool (owner DM only, always offered there so the tool list in the cached prefix never changes) keeps one `kv` entry `preset:task` with a reason and an end time; `for_chat` swaps the shared vibe for the assistant preset while it is in force and the chat has no pin, and the owner's messages push the end 30 minutes forward. The daily pick and `switch_vibe` are untouched.

As built (W17, revised 2026-11-21 to trim by prompt tokens, not message count): `dom/window.py`. A chat's window starts at a stored message (kv `window:<chat id>`: its row id and time, plus the prompt's measured fixed part) and only grows until the estimated prompt reaches `window_budget_tokens` (32,000); one trim then drops the oldest messages until about `window_keep_tokens` (20,000) are left, never fewer than 4 messages. The prompt size is the fixed part (first chat call's reported `input_tokens` minus the window's estimate, measured after each turn; 6,000 until the first measurement) plus an estimate of one token per three UTF-8 bytes for every message in the window. `window_size` (500) is a safety bound that also triggers a trim. A trim never drops a message past the memory cursor: it is blocked, the dispatcher starts a memory pass, and the trim lands in the next turn with the note rewrite. Timings are `name@ms` strings in `turns.trace`. Checked before the window in the prompt: the system message and tool list are stable per turn (`task_mode` is always offered, never conditionally); the only per-turn items after them are the preset layer, notes and participants' notes, which change rarely; the turn note stays last.
