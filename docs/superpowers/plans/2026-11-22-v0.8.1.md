# v0.8.1: fast, quippy and in your control

North star (owner, 2026-11-22): the ultimate personality-driven agent that runs on a local
stack, with the cloud as fallback, so people without the owner's hardware can still run it.
v0.8.1 makes Dom feel fast and gives the owner control over models, memory and leftovers.
The new dashboard frontend runs alongside as its own track (F) and ships when it is ready.
Baseline: the design spec, the roadmap, the v0.8.0 plan and the decisions recorded here.

## How a reply is timed today

Measured on the Pi (Jev scan, 2026-11-21, 47 model turns). Owner DM median 37 s from message to
first bubble, groups 25 s.

| Stage | Owner DM median | What it is |
|---|---|---|
| Message → turn start | 5.3 s (p90 66 s) | the 2–6 s debounce (capped at 15 s from the first message), plus waiting for a running turn, media, or a sleeping DM |
| First model call | 16.8 s | a 16–25k-token prompt, often missing the prefix cache |
| Later model calls | 2.9 s each | 2–3 calls per turn, often bookkeeping only (`extend_online`, refused `switch_vibe`, `skill_view`) |
| Typing and sending | 10.2 s (groups 16.6 s) | 8 characters a second per bubble; thinking time only reduces the 30 s total cap |

Telegram does not tell bots when someone is typing, so "is the sender done?" can only be judged from
the messages themselves. The debounce already has a 15 s cap; the long tail comes from the other waits.

## Workstreams

### W1 Measure every stage (E36)

- Store per-turn timings for each stage: debounce, lock wait, media wait, asleep, triage, each model
  call (with `cached_tokens` and the split prompt hashes), tools, typing.
- A timing view on the dashboard: one row per reply, a bar per stage, filters by chat.
- Dom never sees the numbers (E46). When a reply goes out late, the turn note only says he is answering
  late, so he can give an in-life reason if it fits.
- Done when: the owner can open any slow reply and see which stage took the time.

### W2 Triage on arrival (E36, E38, E44)

- Run Jev when a message arrives, not after the debounce. Typing, the reaction and the owner-DM
  "on it" line fire from it. Log Jev's choice and confidence.
- Jev answers "is the sender done?". If yes, skip the debounce; otherwise keep it, still capped at 15 s.
- Early start (E45): once Jev says ready, the turn starts. A message that arrives before the first
  bubble is sent cancels that answer and restarts it with the new message (the prompt prefix is cached,
  so a restart is cheap). One that arrives after starts a follow-up turn.
- Ordering for the follow-up: the window stays in arrival order. Each of Dom's bubbles carries the id
  it replied to, and the turn note says which messages came in while he was answering and that his
  earlier bubbles had not seen them, so he adds to or corrects what he said instead of repeating it.
- "On it" lines rotate and are rate-limited.

### W3 Adaptive typing (E37, E38)

- A bubble's typing time is the human-like time for its length minus the time already shown as
  "typing…" while thinking, never below zero. A fast endpoint gets the pause; a slow one adds nothing.
- Short quips in groups go out fast. Assistant mode types faster. The 30 s cap per reply stays.

### W4 Fewer model calls (E36, E44)

- Jev picks the skill ahead of the call and puts it in the turn note; `skill_view` stays as the fallback.
- The turn note says when a vibe switch cannot work, so the model stops making refused calls.
- Staying online longer is decided by Jev after the turn, not by a model call.
- Done when: bookkeeping-only extra calls drop to near zero in the W1 view.

### W5 Prompt cache (E44)

- A fixed-shape tool list: shared tools first, owner-only tools last. Scopes stay separate, so groups
  never see owner-only tool names.
- Notes are saved as often as needed but swapped into the prompt only at a window trim or on a slow
  cadence; a "notes updated since …" line goes at the end of the turn note. MEMORY.md refreshes at most hourly.
- Done when: the W1 view shows the owner DM's first call hitting the cache on most turns.

### W6 Model routing and settings (E39)

- One role per model use: chat, fallback, media, drafting. Each role has a primary provider (a local
  endpoint or a cloud one) and an ordered fallback chain. Jev stays the TypeSafe Decisions API: it is a
  classifier, not a chat model, so it is not swappable to one.
- A settings API that validates changes, runs a real test call, and writes `config.toml`. API keys stay
  in `.env`; the dashboard shows whether a key is set, never its value.
- The current dashboard gets a plain settings page; track F gives it the real design.
- Every cloud provider is checked against the zero-data-retention rule with a real call before use.

### W7 Delete and retire (E40)

- Skills, plugins: retire (off, files kept) and delete (files and records removed).
- Reminders: cancel and delete. Desktop and self-directed task history, approval cards: delete.
- Owner-only, from the dashboard and the owner DM. Each removal is recorded as an owner event.
- A delete takes a backup first.

### W8 Memory self-edit (E41)

- A setting, off by default. When it is on, Dom can propose an edit to a note (USER.md, NOTES.md,
  journal, people and chat notes) in the owner DM only.
- Each proposal is a diff on an approval card; nothing changes until the owner approves. Private notes
  never appear in a group.

### W9 Plugins (E44)

- Per-plugin storage: one JSON blob of about 64 KB through the `_dom` helper.
- Test-run a plugin in the sandbox before the owner approves it; the card shows the result.
- Drafts use Claude Haiku 5.5 at low or medium thinking, once it passes a real call under the ZDR key.

### W10 Error handling leftovers

- Telegram flood control (`TelegramRetryAfter`) and unguarded `send_chat_action`.
- A long bubble is split (counted in UTF-16), not retried.
- Forum topic replies after a restart or catch-up; supergroup migration (`migrate_to_chat_id`).
- `NoFinalAnswer` in friends' and groups' chats; a friend under the spend cap gets a line, not silence.
- A clearer owner note when a private action has no eligible receiver; the `react()` result; a text
  fallback for a failed sticker or GIF; critical reminders are not given up after MAX_ATTEMPTS.

### W11 Sticker previews (E44)

- Each sticker in a set gets a short description from the media model, cached, so Dom sees more than
  the emoji alias.

### W14 In character about his own machinery (E46)

- The turn note keeps what Dom needs (how long he stays online, what arrived while away), but the frame
  tells him never to say it as mechanics: no minutes left, restarts, versions, timings or tool names in
  his replies. Wrapping up gets an in-life reason instead.
- Owner DM exception: when the owner asks directly about Dom's setup, or in assistant mode, he can answer plainly.
- Done when: a replay of recent turns has no reply stating minutes left, a restart or a version unprompted.

### W12 Live verification

Verified on the Pi against real Telegram. Rows say exactly what was tested live and what by tests only.

- Owner DM and group: message to first bubble before and after, from the W1 view.
- The "sender done" skip, and the 15 s cap with a burst of messages.
- A fast and a slow endpoint: typing adapts (W3).
- Switching the chat role's provider in settings, a test call, and a fallback when the primary is down.
- Retire and delete each kind of item; the backup exists.
- Memory self-edit: off by default; on, one proposal approved and one rejected.
- A plugin with storage, test-run before approval.

### W13 Release gate

A drift pre-review (one reviewer) runs once about half the workstreams are merged, so findings come
early. Then, as in the `dom-release` workflow: two fresh drift reviews (Gemini 4 Neon at xhigh, Claude Fable 5.2
at medium) over every spec, plan and owner decision, repeated until both find zero. Then tag, release
and `/update`.

## Track F: the new dashboard (E42)

Runs alongside v0.8.1 and ships in the first release after the owner signs it off.

- Stack: Svelte with Vite, built as a static app that Dom serves from the same origin. Login stays
  Cloudflare Access; requests stay same-origin; the CSP stays self-only.
- Dom gains a JSON API, one page at a time, while the current pages keep working until each new page replaces them.
- Builds happen in GitHub Actions (dev builds on the Mac). The built files go into the release commit, and CI checks they match
  the source, so `/update` keeps deploying a tagged tree with `uv sync` and the Pi never runs Node.
- Baseline first: design tokens, a component library in Storybook, and phone and desktop screenshot
  baselines. Opus 5.5 or Sonnet 5.5 builds the baseline with Home, Chats and Settings; the owner iterates
  until it is right; then the other pages are ported to it and checked against the baselines.
- Plugin panels keep returning structured data; the app renders them. Plugins never ship HTML or JavaScript.

## Build order

- Wave 1, in parallel (separate files): W1 timing, W7 delete and retire, W9 plugins, W10 error handling,
  W11 sticker previews, track F baseline.
- Wave 2, after W1 so the gains are measured: W2 and W3 (both in dispatch, one delegate), W4, W5, W6, W8, W14.
