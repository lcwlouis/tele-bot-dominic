# v0.8.2: one Dom across every chat

North star (owner, 2026-11-22): the ultimate personality-driven agent on a local stack, with the cloud as fallback.
v0.8.1 made each reply faster and gave the owner control. v0.8.2 makes Dom one mind across his chats: a central
attention loop that visits chats in turn, carries what he was just doing, and can pass things between chats with the
owner's approval. It also brings the phone remote-desktop viewer, asking before escalating to a bigger cloud model,
search on the owner's own SearXNG, the next speed step, and the new dashboard (track F2), which comes last.
Baseline: the core design spec, the v0.8.1 plan and the owner decisions recorded here and in earlier plans.

v0.8.2 work builds alongside the v0.8.1 release gate, but nothing merges to `main` until v0.8.1 is tagged.

## Workstreams

### W1 Faster first bubble (E49)
- First-bubble "typing…" only when the reply came back faster than the human-like time for its length (the W3 credit already
  holds the time shown); otherwise send at once.
- Sender wait 2–4 s while online (keep the 15 s cap and Jev's skip as they are).
- Find out why the home-lab model's prefix cache misses on first calls (`cached_tokens` 0 on Dominic Dev): log the prefix
  hashes against the server's cache behaviour, then fix what is ours.
- Done when: the W1 view on Dominic Dev shows message → first bubble at least 3 s faster on the owner DM with a fast model,
  and the cause of the cache misses is known.

### W2 Central attention loop and cross-chat queue (E52, D1, D2): spec first
- A design spec in `docs/superpowers/specs/` before any code, from the backlog design: one awake loop visiting chats in turn;
  Jev sorts arrivals into next/later; owner DM first; waiting chats bumped by age; a per-chat cap; a facts-only "what I was just
  doing" note at the end of the turn note (never quoted messages; leak rules apply); cache layout kept (shared system message,
  per-scope tool list, per-chat user message); a queue + worker that owns every cross-chat action so no turn takes another
  chat's lock; approval cards for risky directions; measure vLLM cache eviction rather than assume it holds.
- The owner reviews the spec; then the build.
- Done when: two chats active at once are answered in turn without one starving, a group asking for the owner pings the owner DM,
  Dom can send his own note to the owner DM from any chat with no card (D2), and a DM→group message goes out only after the owner approves its card.

### W3 Phone remote-desktop viewer
- From the Fable UX scan (backlog): a full-page viewer with Done, the live host and a countdown, opened from the handoff link;
  auto-reconnect; local zoom and pan (pinch no longer zooms the remote browser); a key bar; one-finger scroll; Copy/Paste
  buttons (never automatic remote→local; clear the remote clipboard at Done); room for the on-screen keyboard; fullscreen;
  "phone mode" = resize the remote screen during a handoff and restore 1280x1024 at Done (no CDP mobile emulation).
- Auto password mode: the viewer switches to password entry when the focused remote field is `input[type=password]`, read
  through the sandbox API and treated as hostile input; passwords never go through `page/type`.
- The viewer stays its own noVNC page, so it does not wait for the new dashboard.
- Done when: a sign-in handoff can be finished comfortably on the owner's phone, password field included.

### W4 Ask before escalating to a bigger cloud model (D3)
- A new `escalation` role in model routing (W6 of v0.8.1). Dom asks on an owner-DM card when D3's condition is met, showing the
  model and an estimated cost; the owner's choice applies to that task only. Never automatic; never in groups.
- Spend cap and usage attribution as for every call; a ZDR check for an OpenRouter escalation model.
- Done when: a long owner-DM task produces the card, Switch runs the rest on the cloud model, Keep local continues as before.

### W5 Search on the owner's SearXNG (E50, D4)
- Search becomes a role with a fallback chain, like the others: SearXNG (JSON API on its LAN address, set in config only) first,
  then the cloud providers the owner picks (D4: OpenRouter web, DeepSeek web search, Tavily; each needs only its key). SearXNG returns results, not an answer: Dom gets the top results (title, URL, snippet) as untrusted
  web content, or the chat model summarises them, whichever keeps the reply path faster.
- Settings shows the search role with Test, like the others. The owner checks SearXNG's JSON output is enabled.
- Done when: a question that needs the web is answered from SearXNG with the cloud fallback unused, and works again with
  SearXNG stopped.

### W6 Edge cases left from v0.8.1 reviews
- Forum catch-up scoped per topic (prompt, unread tracking and reply target), General included.
- A supergroup upgrade raised mid-reply: the message being answered gets its reply in the new chat.
- A critical reminder does not resend chunk 1 after a restart mid-send.
- The 30-min group no-answer cooldown survives a restart.
- A flood-limited catch-up that sent nothing is retried as a catch-up, not a plain online turn.
- A reaction followed by a flood-limited first bubble does not count as answered; the model's reaction is sent after the send
  boundary so a restart cannot react twice.
- `find_devices` lists Dom once, not once per Pi interface.
- Done when: each has a regression test.

### W7 New dashboard, track F2 (E51, D5): last
- The JSON API for each page first (Dom keeps serving the current pages until each new page replaces them), then the Svelte app:
  design tokens from Quiet Orbit, shadcn-svelte components restyled, a Storybook of every component, phone and desktop
  screenshot baselines under Dom's CSP, built in GitHub Actions with the built files committed so `/update` and the Pi never
  run Node.
- Order: Home (with the animated orbit), Settings (Models, Providers, permissions; phone Settings redesigned), Memory (phone
  file view redesigned), Chats (with "Tune with Dom"), Work/Desk, then the rest.
- The owner iterates on the baseline before the other pages are ported.

### W9 Release gate
As in the `dom-release` workflow: a drift pre-review at about half way, then two fresh drift reviews (Gemini 4 Neon at high,
Claude Fable 5.2 at medium) over every spec, plan and owner decision, repeated until both find zero. Then tag, release and
`/update` (the real Dom gets only a short check after `/update`; live tests run on Dominic Dev).
