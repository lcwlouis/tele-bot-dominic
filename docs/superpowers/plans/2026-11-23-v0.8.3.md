# v0.8.3: Dom's voice and face, and models you can pick properly

North star (owner, 2026-11-22): the ultimate personality-driven agent on a local stack, with the cloud as fallback.
v0.8.2 made Dom one mind across his chats and gave him a new dashboard. v0.8.3 gives him a voice and a face, made on the owner's own hardware. It also makes choosing models easy and adds the first two items from the v0.8.x roadmap: memory export and global search. The provider and model screens are rebuilt around what each provider actually offers.

Baseline:
- the core design spec;
- the v0.8.1 and v0.8.2 plans;
- the roadmap `docs/superpowers/plans/2026-11-23-roadmap-v0.8.x.md`;
- the owner decisions recorded here and in earlier plans.

The studio design comes from the Phase 9 studio plan, which the owner approved on 2026-11-20 (its D1–D6). That draft lives outside the repo because it names hosts and people. W1 starts by moving a scrubbed copy into `docs/superpowers/specs/`.

### W2 Models and providers rework (E56, D8, D9)
- Provider setup moves to the Providers tab: add, edit, test and remove a provider (name, address, key variable, kind). The Models tab then picks, per role, a provider and a model from that provider's list, plus the fallback chain as today.
- Model lists are fetched per provider and cached in the store for a day, with a refresh button. A model ID can always be typed by hand. Each model shows whether it reasons; reasoning effort offers what the provider supports (D9).
- Triage becomes editable like the other roles, with a test call that uses Jev's real decisions request. It is ready for more decision models later.
- Every rule from v0.8.1's PR #11 stays:
  - a key variable that already holds a value is never assigned to a new host;
  - new providers get an empty variable name;
  - saves are tested first, written atomically, and keep `.bak`.
- Done when the owner can add a provider, pick a model from its fetched list with an effort level, edit triage and test it, all from the phone, without touching `config.toml`.

**Done (W2, branch `v083-models`).**
- Providers tab: add, edit, test and remove providers, saved as `[providers.<name>]` tables (kind, base URL, key variable). Addresses the roles already use show as unsaved providers; Edit names and saves them. Editing a provider's address or key moves every slot that uses it, in one atomic save. A provider a role uses can't be removed. Saved providers pair their key like a role does, so every PR #11 rule holds.
- Model lists (D8): `dom/model_lists.py` fetches OpenRouter or any OpenAI-compatible `/models` (one GET, 10 s, 8 MB cap, no redirects, key only to its paired host), cached in kv for a day, with Refresh. Jev and the search kinds don't list models; an ID can always be typed.
- Effort (D9): config takes any lowercase effort word; a save checks it against the fetched list when it knows the model (none for a model that doesn't reason), else allows the usual names. The editor offers the model's levels with the cost note.
- Models tab: per slot, a provider then a searchable model picker, plus a custom address. Move up on every fallback in the card view (the first becomes the primary), untested. Triage is a role (one endpoint, no effort) under "Decision models"; its test is a real decisions request, and a save swaps Dom's Jev client without a restart. The studio cloud chains from #52 show as their own group with Move up; adding or changing them stays in `config.toml`.
- Review fixes (PR #53): the key pairing is checked on the routes as saved, after the starter's defaults fill a blank key, before any probe; model-list entries holding any configured secret value are dropped (on fetch and on cached reads); a hand-written provider address gets the URL rules before its list is fetched; a provider move tests every changed slot as it will be sent, effort included (probes with an effort get 2048 tokens), and role saves now test an effort change; every save builds its routes and clients before replacing `config.toml`, so a failure keeps the old file and runtime; a triage key added after saving takes effect on Test or on the next save, and the UI says the leak check is off until then; docs/deploy-pi.md and the changelog say how to roll back past a saved `high` effort.
- Live-only, for main: real OpenRouter and home-lab `/models` lists (and whether OpenRouter's list shape still says which models reason), a real Jev decisions test, and the whole flow from the phone on Dominic Dev.

**Done (W2 follow-up, branch `v083-provider-presets`).**
- The Providers editor fills editable fields from 13 server-owned presets. OpenRouter chat keeps its fixed zero data retention policy. Preset saves use the existing key pairing checks.
- A chat route exhausted by OpenRouter or direct DeepSeek budget refusals shows the owner a private system notice once per reset window. Home and `/status` show the same restriction until its reset or a successful turn. When OpenRouter gives no reset, a successful turn clears the status and re-arms the notice.
- Direct DeepSeek uses the existing compatible route, prefers `deepseek-flash` for new model slots, disables thinking without changing fallback behavior, and estimates USD spend from its token breakdown. Settings recommends zero data retention when a cloud route needs a policy review.
- Live only, for main to verify: check a real refusal and recovery on Dominic Dev, and try preset setup with actual credentials and model lists.

### W3 Memory export and global search (R1, R2, D10, E62)
- Export as D10 describes. The zip is built off the event loop with a size cap, and the download is owner-only and logged as an owner event.
- Global search is one box in the dashboard's top row, also reachable from the phone menu. It searches chats (FTS5), memory files, briefs, reminders, desktop tasks, skills and plugins. Results are grouped by kind, and each opens its page.
- Privacy: the owner DM shows in full. Other chats show at most a one-line preview, and the API returns no more than the page shows.
- Dom's tool (E62): `search` replaces `search_history` in the owner DM and covers the same kinds of item as the dashboard. In a group or a friend's DM the tool keeps today's scope, that chat's own history only, so nothing from other chats, memory files or private notes can surface there. The scope is enforced in code, not by the prompt.
- Done when an export opens and holds every memory file, and a search finds a word in each kind of item while other chats show only previews. Dom's tool finds the same items in the owner DM and only that chat's history elsewhere. API and tool tests cover both.

**Done (W3 and W9, branch `v083-search-memory`).**
- Export: `dom/memory_export.py` zips `SOUL.md`, `memory/`, `private/`, `skills/`, `presets/` (never `.env`, `state.db`, backups, `.bak` files or links), capped at 20 MB, built in a thread. `GET /api/memory/export` (owner-only, owner event) and `/export` in the owner DM.
- Search: `dom/global_search.py`, used by `GET /api/search` and Dom's `search` tool. Other chats' messages are cut to a one-line preview inside the module. Dashboard: a search box in the desktop top row, a search icon on the phone, a menu link, and a `/app/search` page; memory hits open their file (`/app/memory?file=`).
- The tool: one `search` tool in every scope, keeping the shared tool prefix cache-stable. The owner DM gets the global search; elsewhere the handler searches that chat's history only (the old `search_history`, renamed).
- W9 / D12: a group pass gets `GROUP_RULES` in its system prompt and a `purpose` on each note; the file targets were already fixed per scope. `docs/privacy.md` describes both.
- Live only, for main to verify: an export opened on the real home, a search across each kind from the phone, and asking Dom in the owner DM and in a group.

### W9 Memory across chats (D12)
- Today:
  - a friend's DM writes only that DM's own notes;
  - group passes write the group's notes, the participants' people notes and the shared `MEMORY.md`;
  - every chat reads `MEMORY.md`;
  - a group or DM reads the people notes of its participants.

  So what a friend says in one group can surface in another group, or, through `MEMORY.md`, in someone else's DM. What a friend tells Dom in a DM never leaves that DM, apart from the owner DM's facts-only "elsewhere" lines.
- v0.8.3 tightens the memory pass rules per D12, with tests that a group-specific fact lands in that group's notes.
- v0.8.4 carries the source-tagged notes (roadmap R13).
