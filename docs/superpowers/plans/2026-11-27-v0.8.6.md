# v0.8.6: Dom's own calendars, booking, a shared workspace, more Google, and a desk for everyone

North star (owner, 2026-11-22): the ultimate personality-driven agent on a local stack, with the cloud as fallback.

v0.8.5 gave Dom hands, a world and a window. v0.8.6 makes those hands useful day to day:
- his own calendars, and bookings within the windows the owner okays;
- one workspace that he and his desktop share;
- Drive, Docs, Sheets and Contacts;
- a separate desktop for requests from groups and friends;
- the news overnight;
- a pilot of a subscription agent through ACP.

- the post-v0.8.5 backlog (memory note `post-v085-backlog`) and its "Narrowed in the build" list;

## Workstreams

### W1 Dom's own calendars (E109)
- **Scope:** add `calendar.app.created`. Dom's calendar tool gains `create_calendar`, which asks with an approval card the first time for each new calendar.
- **Writes:** add, move and delete go only to calendars Dom created. Code checks the target calendar id against the list he made; Google enforces it too.
- **Reads:** reads stay on the owner's chosen calendars.
- **Nudges:** each event on Dom's calendars can carry a nudge time. Dom reminds the owner before it, through the existing reminder system, in the owner DM only.
- **Dashboard:** Settings → Services → Google lists Dom's calendars and the read and write switches.

### W2 Booking (E110, D23)
- **Where:** friends' DMs and groups (D23).
- **Windows:** the owner sets them in the owner DM ("weekday evenings 7 to 10, Saturday afternoons") or on the dashboard, and they are stored as structured windows.
- **Flow:**
  - a friend asks to meet;
  - Dom offers up to three slots that are inside a window and free on every calendar he reads;
  - the friend picks one;
  - the owner gets a card with the friend, the time and the context, and approves or rejects;
  - only then does Dom confirm to the friend and add the event to his booking calendar.
- **What leaves:** only the times. Nothing else about the owner's calendar leaves the owner DM, and code filters it.

### W3 The shared workspace and files (E112, D22)
- **Workspace:** `<home>/workspace` is mounted into the desktop sandbox at `/workspace`. Downloads and Dom's own files land there, so the inbox and outbox become a view of it, not a copy.
- **Telegram files:** documents sent to Dom (in the owner DM; elsewhere only with the sharing toggle) land in the workspace. Dom reads text, Markdown, CSV and PDF text.
- **File tools:** owner-DM `files` tools (list, read, write and move within the workspace) with size caps.
- **Dashboard:** a Files page browses the workspace and Dom's readable home files (memory, media, briefs, skills). Its upload and download stay behind the dashboard's auth.
- **Permissions:** the existing download and upload permissions still apply when a file leaves the sandbox through the browser.
- **Sharing toggle (D22):** "Let groups and friends read the shared folder", off by default. With it on, they can read `workspace/shared/` only, and never write.

### W4 More Google: Drive, Docs, Sheets and Contacts (E113, D21)
- **Switches:** each has its own switch and scopes, following W4's pattern (approval cards for writes, owner DM only, untrusted fencing).
- **Drive:** search and read the files Dom may see; create in his own folder.
- **Docs and Sheets:** read; create and append in his own files; every edit through a card.
- **Contacts:** read only, to find who a friend is and their email for booking or drafts.
- **Sharing by link (D21):** when the owner sends a Drive or Docs link, Dom answers with a dashboard link that opens Google's file picker on that file. One click grants Dom that file.

### W5 A separate desktop for groups and friends (E111)
- **Requests:** a group or friend asks, Dom proposes a desktop task, and the owner gets a card (Reject or Allow once).
- **Where it runs:** on a separate desktop container with no saved logins and none of the owner's sessions, on another configured host if there is one; otherwise on the Pi, one at a time, with the owner's logins locked out.
- **Limits:** a step and spend limit per group. Only the final answer goes back to the chat.
- **Before building:** measure the memory of one more sandbox on each host.

### W6 Overnight news (E108)
- **Collecting:** part of the nightly background work. A few headlines and nearby events for the `[world]` place, found with the search route, kept as `memory/NEWS.md` with dates and sources and replaced each night.
- **Prompt:** the "world now" block adds one or two lines from it.
- **Spend:** it obeys the spend caps as background work, and it is off when search isn't set up.

### W7 ACP pilot (E114, D20)
- **Provider:** an `acp` provider kind, with Codex (`codex-acp`), Claude (`claude-agent-acp`) and Antigravity (`agy acp`) as separate entries, each with its own switch, off by default and warned as not ZDR. Owner DM only, as a drafting or escalation role. They run on the Pi where the agent's binary supports it, otherwise on a Mac host.
- **Tools off:** each agent's built-in tools are switched off where the agent allows it, and every permission request is refused.
- **Measure:** latency, quality against the current chat model, and failure modes. The Trace view shows it.
- **Decide:** keep it, or drop it before the gate. **Decided (main, 2026-11-27):** keep Codex and Claude, off by default, provided the W9 live check shows their built-in tools are really off (an agent asked to run `ls` runs nothing); one that fails is blocked like Antigravity before the tag. **Outcome (main, 2026-11-27):** Claude passes with the stricter settings above; Codex fails (its MCP servers and plugins stay on) and is blocked like Antigravity, so only Claude can be switched on in v0.8.6.

### W8 v0.8.5 live-test fixes (first)
- **Bot change:** a new bot token (the handle move) left the owner DM's read marker at the old bot's message id (3497, while the new ids run from about 1 to 70), so Dom saw nothing unread and never woke while offline. It was fixed in the Pi's data on 2026-11-27. The code fix: store the bot id, and on a change reset each chat's read markers to the newest message under the new bot.
- **Studio health:** probes have a 3 s deadline and about 8% fail over the studio Mac's Wi-Fi. Each failure marks the studio away for 60 s, which sends media to paid backups. Fix: a 10 s deadline, keep the last good health through one failed probe, and log the request path.
- **Reactions (owner: keep an eye on them):** each rejected reaction records Telegram's reason, the emoji and the target message in the log, the turn's steps and its trace. The Turn log shows a "reaction rejected" chip, and the System page counts rejections over the last week, so a pattern shows. Main checks the real Dom's log for them during W8.
- **Dashboard:**

  - no "Quiet Orbit" subtitle;
  - a slimmer sidebar (the Workspace list repeats the Work and System tabs);

### W11 Media: spontaneity and video understanding (E115, E116)
- **Spontaneity:** a setting (Settings → What Dom may do → Media) from "rarely" to "often", with a default near today's behaviour. It scales the prompt line and the rolling limits within the owner's caps.
- **Frame strips:** incoming videos, video notes and animations become a frame strip (a grid of evenly spaced stills) plus an audio transcript (the media route's speech-to-text, or the chat model if it takes audio), given to the chat model when it can't take video natively.
- **Long videos:** sample adaptively (more frames for longer clips, up to a cap), split very long clips into chunks summarised in turn, and drop the 8 MB skip for this path.
- **Keep:** the strip, so later turns can look again; it goes into Dom's aged-media description.

## Narrowed in the build

- **W7: Antigravity cannot be switched on.** An agent is enabled only when Dom can switch its own tools off. `agy acp` (v1.5.13) takes no per-session settings or mode (`--settings` and `--mode` are `agy` flags, and `agy acp` rejects them); its only tool rules are the `permissions.deny` list in the owner's global `~/.gemini/antigravity-cli/settings.json`, which Dom neither writes nor can check, and refusing permission requests is not enough because auto mode runs sandboxed commands without asking. So its switch shows "no way to turn its tools off yet" and the client refuses it before spawning. Revisit when `agy acp` takes per-session tool rules.
- **W7/W9: Codex cannot be switched on either.** Main's live check (2026-11-27, `codex-acp` 0.16.0) found that `INITIAL_AGENT_MODE` and `CODEX_CONFIG` switch off only its shell and search: the owner's `~/.codex/config.toml` MCP servers and plugins (computer use, a Node REPL, browser, Cloudflare) stay on, and `session/new` never answered under them. So it joins Antigravity in `ACP_NO_TOOLS_OFF` with the reason "it loads your own MCP servers and plugins, which Dom can't turn off yet". Revisit with a dedicated `CODEX_HOME` holding only the auth file and an empty config. Claude's `tools: []` was not enough either (the owner's MCP servers and claude.ai connectors were still offered); it now also gets `strictMcpConfig`, no `mcpServers`, no `settingSources` and `ENABLE_CLAUDEAI_MCP_SERVERS=false`, under which two runs made no tool call.
- **W5: guest tasks run only in a container Dom starts and removes himself.** E111's "another configured desktop host" is left for later: Dom cannot reset a remote sandbox, so one chat's cookies and sessions would reach the next. The `guest = true` host option is gone (a config that sets it is refused at load), and every guest task starts a fresh `guest` container on the local host and removes it when it ends, with a sweep at restart. Remote guest hosts can return when a remote sandbox can be reset between tasks.
- **Accepted builder departures** (main, after review): W2 counts the minimum notice from when a time was offered; W3's 500 MB workspace cap is soft (checked between desktop actions, fresh at a task's start and end) and the desktop can read the whole workspace it mounts; W4 asks only for `drive.file` and `contacts.readonly`, creates only Docs and Sheets, makes no picker link for folders, lets a saved Allow always skip the card, and sends a write whose content a Telegram card cannot show exactly to the dashboard; `contact_email()` exists but booking does not call it; W5 guest tasks get only the read-only text browser, never mount the shared folder, decline a second guest request while one runs, and show their limits read-only; W7 starts a fresh agent process per call with no daily call budget, and turns Dom starts himself never reach an agent; W8a keeps an unproven suspected switch open, re-judged at each start (`dom doctor` shows it), and supergroups are never moved.
